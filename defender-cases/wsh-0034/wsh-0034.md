## WSH-0034 ASR rule AsrRansomwareBlocked is triggered

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0034 ASR rule AsrRansomwareBlocked is triggered"_ has been created, how to use it.

### Required Access

These hunting cases are linked through a published application that grants us permission to perform threat hunting via the API in our customers' security portals.

### Custom Changes

* No custom changes are made.

## Overview

Detects when the ASR rule AsrRansomwareBlocked is triggered. MDE uses client and cloud heuristics to determine of a file resembles ransomware. This file could for example be the script that is used to encrypt files. No alert is generated by default by Defender For Endpoint. This could be the start of a ransomware attack. Additional information available by Microsoft.

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **Device Protect** module.

### How to Detect?

Detects when the ASR rule AsrRansomwareBlocked is triggered.

### KQL

```kql
    let WhitelistedCommandLine = dynamic([
        @"C:\ProgramData\CentraStage\Packages\c210df93-fb04-4ffa-b2fb-a8d779b17382#\command.ps1"
    ]);
    let ShareXPath  = @"^C:\\(Program Files( \(x86\))?|Users\\[^\\]+\\AppData\\Local\\Programs)\\ShareX(\\|$)";
    let DAZzlePath  = @"^C:\\Program Files( \(x86\))?\\Endicia\\DAZzle64(\\|$)";
    let ShareXImageEditorHashes = dynamic([
        "9fcf5fd85eea6b73a6679e45fa1a30c2e4282738",
        "c7b52293dbb74ff3bff6f95aa45e6fadf027ad68"
    ]);
    let DAZzleHashes = dynamic([
        "f9152ba0412575cebbc38c6923a7ff9ea89a1ba8"   // re-seed on each DAZzle version bump, else FP returns
    ]);
    DeviceEvents
    | where Timestamp > ago(1d)
    | where ActionType =~ 'AsrRansomwareBlocked'                                   // block-only; audit dropped to limit noise
    | where not (InitiatingProcessCommandLine has_any (WhitelistedCommandLine))   // moved up: per-event filter
    | extend SHA1lc = tolower(SHA1)
    | extend IsTrustedApp = case(
    FileName =~ "ShareX.ImageEditor.App.exe"
        and FolderPath matches regex ShareXPath
        and set_has_element(ShareXImageEditorHashes, SHA1lc),
        true,
    FileName =~ "ShareX.exe"
        and FolderPath matches regex ShareXPath,
        true,  // path-only trust until you seed hashes; tighten later
    FileName =~ "DAZZLE64.EXE"
        and FolderPath matches regex DAZzlePath
        and set_has_element(DAZzleHashes, SHA1lc),
        true,
    false)
    | where not (IsTrustedApp)
    | summarize
    TotalEvents          = count(),
    TriggeredFiles       = make_set(FileName),
    FileHashes           = make_set(SHA1),
    FolderPaths          = make_set(FolderPath),
    InitiatingProcesses  = make_set(InitiatingProcessCommandLine),
    InitiatingFolders    = make_set(InitiatingProcessFolderPath),
    FirstSeen            = min(Timestamp),
    LastSeen             = max(Timestamp)
    by DeviceName, AccountName
    | project DeviceName, AccountName, TotalEvents, TriggeredFiles, FileHashes, FolderPaths, InitiatingProcesses, InitiatingFolders, FirstSeen, LastSeen
```

## How to Investigate?

1. Validate the ASR trigger context
   - Confirm the AsrRansomwareBlocked rule fired and the activity was blocked
   - Identify the file names and hashes involved in the detection

2. Analyze the initiating process
   - Inspect the full command line that triggered the rule
   - Check execution path and parent process behavior
   - Confirm the process is not part of known automation or management tooling

3. Assess user and device behavior
   - Review what the account was doing at the time of the event
   - Check if the activity aligns with normal user workflows
   - Identify if the device has a history of similar alerts

4. Correlate with file activity
   - Investigate whether the triggered files were newly created, downloaded, or modified
   - Check file locations for user-writable or temporary directories
   - Look for naming patterns tied to ransomware staging

5. Timeline reconstruction
   - Build a sequence of events before and after the ASR alert
   - Correlate with script execution, archive extraction, or macro activity
   - Identify any parallel suspicious processes on the same host

6. Scope for related activity
   - Search for the same file hashes on other endpoints
   - Look for repeated ASR triggers across multiple devices
   - Identify potential campaign-style behavior patterns
