## WSH-0065 RoguePlanet Defender Remediation Abuse for SYSTEM Privilege Escalation

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0065 RoguePlanet Defender Remediation Abuse for SYSTEM Privilege Escalation"_ has been created, how to use it.

### Required Access

These hunting cases are linked through a published application that grants us permission to perform threat hunting via the API in our customers' security portals.

### Custom Changes

* No custom changes are made.

## Overview

RoguePlanet is a Windows local privilege escalation (LPE) proof of concept that turns standard-user code execution into an interactive `NT AUTHORITY\SYSTEM` shell. Rather than attacking the kernel, it manipulates Microsoft Defender's privileged scanning and remediation workflow so that an attacker-controlled executable is placed where Windows expects the legitimate Windows Error Reporting binary, `C:\Windows\System32\wermgr.exe`. The exploit then manually launches the built-in Windows Error Reporting scheduled task `\Microsoft\Windows\Windows Error Reporting\QueueReporting`, which executes the substituted `wermgr.exe` in a privileged context. The resulting SYSTEM process connects back to a named pipe created by the original user process and launches an interactive console in the user's session.

The chain abuses a time-of-check to time-of-use (TOCTOU) race combined with reparse-point path confusion. It mounts an embedded read-only UDF ISO containing an EICAR test archive named `wermgr.exe`, drives Defender into its detection-and-cleaning path via `MpClient.dll`, monitors for the resulting Volume Shadow Copy snapshot, and uses an NTFS alternate data stream (`:WDFOO`), oplocks, file locks and directory junctions to pause and redirect Defender's privileged file operations. By repeatedly retargeting where trusted paths resolve, the exploit causes Defender's privileged operation to place attacker-controlled content at the protected `wermgr.exe` path. Because the exploit relies on undocumented Defender internals, exact remediation ordering and VSS timing, its success rate varies sharply between machines — the author describes it as hit-or-miss. The PoC was reportedly tested against fully patched Windows 10 and Windows 11 with the June 2026 security updates; at time of writing there is no Microsoft CVE or advisory. This detection favours behavioural correlation over any single indicator, focusing on the highest-fidelity payoff-stage signals.

### Attack Chain

| Stage | Binary / Method | Purpose |
|---|---|---|
| Initial Staging | RoguePlanet.exe (unsigned, user-writable path) | Standard user launches the PoC; creates the named pipe `\\.\pipe\RoguePlanet` and filesystem-churn threads |
| ISO Mounting | `VirtDisk.dll` (`AttachVirtualDisk`) | Mounts the embedded 917,504-byte UDF ISO read-only, without a drive letter, supplying a stable EICAR archive named `wermgr.exe` |
| Defender Trigger | `MpClient.dll` (`MpScanStart`, `MpCleanStart`) | Non-Microsoft process drives a targeted Defender scan and remediation against the EICAR-backed file |
| Race / Path Confusion | NTFS ADS (`:WDFOO`), oplocks, VSS, directory junctions (`FSCTL_SET_REPARSE_POINT`) | Pauses and redirects Defender's path resolution to substitute attacker content and retarget the destination to `C:\Windows` |
| Protected-File Replacement | Defender privileged remediation | Attacker-controlled executable is placed at `C:\Windows\System32\wermgr.exe` |
| Privileged Execution | Scheduled task `\Microsoft\Windows\Windows Error Reporting\QueueReporting` | Manually triggered to execute the substituted `wermgr.exe` as SYSTEM |
| Token Manipulation / Shell | Named pipe `\\.\pipe\RoguePlanet`, `DuplicateToken` / `CreateProcessAsUser` | SYSTEM process duplicates its token into the user's session and launches `conhost.exe` as an interactive SYSTEM shell |

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **DeviceFileEvents** module. The **DeviceProcessEvents** module provides coverage of the SYSTEM-shell payoff stage.

### How to Detect?

This rule correlates multiple payoff-stage signals of the RoguePlanet exploit chain per device within a short time window. It detects: (1) unexpected replacement of `C:\Windows\System32\wermgr.exe` by a process outside the normal servicing chain; (2) creation or access of the distinctive `wermgr.exe:WDFOO` alternate data stream, which has no legitimate use; and (6) a SYSTEM-context interactive shell (`conhost.exe`, `cmd.exe`, `powershell.exe`, or `pwsh.exe`) spawned by `wermgr.exe`. Signals are grouped per device into `CorrelationWindow` time bins. Severity escalates when multiple distinct stages co-occur in the same window, and either the `:WDFOO` ADS or the SYSTEM shell is treated as a high-confidence standalone signal. Because the exploit's success rate varies by host and the binary may be recompiled, this detection deliberately targets durable behaviour rather than file hashes, and should be validated against RoguePlanet behaviour in a lab before tightening. The signal numbering (1, 2, 6) reflects the broader analysis stage set; the manual `QueueReporting` task trigger can be folded in as an additional corroborating signal where required.

### KQL

```kql
   let LookbackWindow = 1d;
   let CorrelationWindow = 10m;
   // Signal 1: wermgr.exe replacement by an unexpected process
   let WermgrWrite =
       DeviceFileEvents
       | where Timestamp > ago(LookbackWindow)
       | where FolderPath =~ "C:\\Windows\\System32\\wermgr.exe"
       | where ActionType in ("FileCreated", "FileModified", "FileRenamed")
       | where InitiatingProcessFileName !in~ ("TiWorker.exe", "TrustedInstaller.exe", "wuauclt.exe", "MsMpEng.exe")
       | project Timestamp, DeviceName, Signal = "1_wermgr_replaced",
                 Detail = strcat(ActionType, " by ", InitiatingProcessFileName),
                 InitiatingProcessFileName, InitiatingProcessAccountName, SHA256;
   // Signal 2: the :WDFOO alternate data stream
   let WdfooAds =
       DeviceFileEvents
       | where Timestamp > ago(LookbackWindow)
       | where (FileName has "wermgr.exe" and FileName endswith ":WDFOO") or AdditionalFields has "WDFOO"
       | project Timestamp, DeviceName, Signal = "2_wdfoo_ads",
                 Detail = strcat("ADS ", FileName),
                 InitiatingProcessFileName, InitiatingProcessAccountName, SHA256;
   // Signal 6: SYSTEM shell spawned by wermgr.exe in an interactive session
   let SystemShell =
       DeviceProcessEvents
       | where Timestamp > ago(LookbackWindow)
       | where InitiatingProcessFileName =~ "wermgr.exe"
       | where FileName in~ ("conhost.exe", "cmd.exe", "powershell.exe", "pwsh.exe")
       | where AccountName has "SYSTEM"
       | project Timestamp, DeviceName, Signal = "6_system_shell",
                 Detail = strcat(FileName, " as ", AccountName, " session ", tostring(InitiatingProcessSessionId)),
                 InitiatingProcessFileName, InitiatingProcessAccountName = AccountName, SHA256 = InitiatingProcessSHA256;
   // Combine and correlate per device
   let AllSignals = union WermgrWrite, WdfooAds, SystemShell;
   AllSignals
   | summarize
       SignalCount = dcount(Signal),
       SignalsSeen = make_set(Signal),
       Details = make_list(Detail),
       FirstSeen = min(Timestamp),
       LastSeen = max(Timestamp),
       Processes = make_set(InitiatingProcessFileName)
       by DeviceName, bin(Timestamp, CorrelationWindow)
   | extend WindowSpan = LastSeen - FirstSeen
   | where (SignalCount >= 2)
        or SignalsSeen has "2_wdfoo_ads"
        or SignalsSeen has "6_system_shell"
   | extend Severity = case(
       SignalCount >= 2, "Critical - multiple stages",
       SignalsSeen has "6_system_shell", "Critical - SYSTEM shell",
       SignalsSeen has "2_wdfoo_ads", "High - WDFOO ADS",
       "Medium")
   | project DeviceName, Severity, SignalCount, SignalsSeen, FirstSeen, LastSeen, WindowSpan, Processes, Details
   | sort by Severity asc, LastSeen desc
```

## How to Investigate?

1. **Confirm the wermgr.exe replacement**
   - Review the `1_wermgr_replaced` signal: verify the `InitiatingProcessFileName` that wrote, modified or renamed `C:\Windows\System32\wermgr.exe` is not part of a legitimate servicing chain (`TiWorker.exe`, `TrustedInstaller.exe`, `wuauclt.exe`)
   - Validate the current `wermgr.exe` against its expected Microsoft signature and hash lineage; an unsigned or unexpected binary at this path is critical
   - Note the timestamp and correlate it with the other signals in the same window

2. **Assess the WDFOO alternate data stream**
   - The `2_wdfoo_ads` signal references the `wermgr.exe:WDFOO` ADS, which has no legitimate use and is hardcoded in the exploit
   - Even a single occurrence warrants investigation; confirm the host and the process that created or accessed the stream

3. **Confirm the SYSTEM shell**
   - Review the `6_system_shell` signal: `wermgr.exe` spawning `conhost.exe`, `cmd.exe`, `powershell.exe` or `pwsh.exe` under a SYSTEM account is the documented payoff
   - Check the parent `wermgr.exe` session ID — the exploit aims to land the SYSTEM context in the user's interactive session, so a non-zero session is the meaningful indicator
   - Genuine `wermgr.exe` does not spawn interactive shells; treat this as high confidence

4. **Identify the originating user and process**
   - Determine the standard-user account that launched the initial RoguePlanet binary; the PoC runs from a user-writable path as an unsigned executable
   - Look for supporting artefacts: the named pipe `\\.\pipe\RoguePlanet`, temp directories matching `%TEMP%\RP_<UUID>` with `\System32` and `\wdtest_temp` subfolders, and a `~917,504`-byte ISO file opened via `VirtDisk.dll`

5. **Corroborate Defender interaction and timing**
   - Look for a non-Microsoft process loading `MpClient.dll` and resolving Defender exports (`MpManagerOpen`, `MpScanStart`, `MpCleanStart`)
   - Look for repeated reparse-point operations (`FSCTL_SET_REPARSE_POINT` / `FSCTL_DELETE_REPARSE_POINT`) on `%TEMP%\RP_*` directories and a user process enumerating `\Device\HarddiskVolumeShadowCopy*`
   - Check for a manual start of the `\Microsoft\Windows\Windows Error Reporting\QueueReporting` scheduled task around the same window

6. **Determine scope across the tenant**
   - Search for the same correlated pattern on additional devices, particularly the `wermgr.exe` replacement and the `:WDFOO` ADS
   - Given the exploit's variable success rate, also hunt for failed attempts (ADS creation or `RP_*` staging without a resulting SYSTEM shell)

## How to Respond?

If the incident is identified as a true positive, proceed with standard remediation actions.

### Custom Remediation Actions

* Immediately isolate the affected device from the network, as a successful exploit yields full SYSTEM control of the host
* Forensically preserve the affected `C:\Windows\System32\wermgr.exe`, any `%TEMP%\RP_*` staging directories, and the mounted ISO artefact before remediation
* Restore the legitimate, Microsoft-signed `wermgr.exe` via System File Checker (`sfc /scannow`) or component servicing, and verify its signature and hash
* Assume SYSTEM-level compromise: rotate credentials and secrets that were accessible on the host, and review for persistence, credential theft and lateral movement performed under the SYSTEM context
* Identify and terminate any attacker SYSTEM processes and child shells; review the originating user account's recent activity and logon events
* Confirm Defender platform and engine versions, and validate whether the installed build remains susceptible; escalate the PoC hash and timeline to Microsoft where appropriate
* Consider attack surface reduction: restrict ISO/virtual-disk mounting and reparse-point creation for standard users, and apply application control (WDAC) to prevent unsigned executables running from user-writable locations
* Do not rely on EICAR blocking alone as a mitigation — the exploit uses EICAR only as a predictable trigger, and blocking it does not address the underlying privileged path-handling issue
