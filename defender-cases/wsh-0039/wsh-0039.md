## WSH-0039 Click Once Application detection

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0039 Click Once Application detection"_ has been created, and how to use it.

### Required Access

These hunting cases are linked through a published application that grants us permission to perform threat hunting via the API in our customers' security portals.

### Custom Changes

No.

## Overview

This hunt is designed to detect potentially malicious ClickOnce applications, which may be used for unauthorized software execution or persistence in an environment. It analyzes process events from the past seven days to identify suspicious executions of dfsvc.exe or files with a .application extension. This hunt checks if common browser and Office applications initiated the process, as adversaries often use these vectors for drive-by downloads. To reduce false positives, the query excludes trusted installation directories like Chrome, Edge, and Office.

A ClickOnce application is a type of Windows application that can be easily installed with a single click from a web browser without requiring administrative privileges. It is commonly used for deploying lightweight software directly to users. However, attackers can exploit ClickOnce to deliver malware disguised as legitimate apps, often tricking users into installing malicious software through phishing links or compromised websites. Once executed, these applications can bypass security controls, execute unauthorized code, and gain persistence on a system, making them a risk if not properly monitored.

### How to Detect?

The query focuses on identifying instances where dfsvc.exe, the ClickOnce deployment service, or .application files are launched, which are common indicators of ClickOnce-based installations.

To refine detection, the query applies the following filters:

*Matches processes where FileName is dfsvc.exe or ends with .application.

* Extracts occurrences of .application within InitiatingProcessCommandLine, ensuring detections even if the filename is obfuscated.

* Flags instances where the initiating process belongs to Chrome, Edge, Internet Explorer, Outlook, or Word, which attackers often abuse for driveby downloads or phishing based installations.

* Excludes trusted execution directories, such as Microsoft Edge, Chrome, and Office installation paths, reducing false positives while maintaining detection fidelity.

The query utilizes ordering to prioritize the latest detections and projects key attributes, such as DeviceName, FileName, CommandLine arguments, ParentProcess, Execution Path, and User Account to facilitate investigation.

### KQL

```kql
  let target      = @"\AppData\Local\Apps\2.0\";
  let startToday  = startofday(ago(0d));
  let startPrev   = startofday(ago(10d));
  let prev = materialize(
    DeviceFileEvents
    | where Timestamp >= startPrev and Timestamp < startToday
    | where FolderPath has target
    | where ActionType in~ ("FileCreated","FileModified")
    | project DeviceName, Path = strcat(FolderPath, FileName), SHA1
    | join kind=leftouter (DeviceFileCertificateInfo | project SHA1, Signer) on SHA1
    | extend FileSigner = coalesce(Signer, "Unsigned/Unknown")
    | summarize PrevSigners = make_set(FileSigner) by DeviceName, Path
  );
  let todayEvents = materialize(
    DeviceFileEvents
    | where Timestamp >= startToday
    | where FolderPath has target
    | where ActionType in~ ("FileCreated","FileModified")
    | project Timestamp, DeviceName, ActionType,
              Path = strcat(FolderPath, FileName), SHA1,
              InitiatingProcessFileName, InitiatingProcessFolderPath, InitiatingProcessSHA1
    | join kind=leftouter (DeviceFileCertificateInfo | project SHA1, Signer) on SHA1
    | extend FileSigner = coalesce(Signer, "Unsigned/Unknown")
  );
  todayEvents
  | join kind=leftouter prev on DeviceName, Path
  | where isnotempty(PrevSigners) and not(set_has_element(PrevSigners, FileSigner))
  | project Timestamp, DeviceName, ActionType, Path,
          FileSignerToday = FileSigner, PrevSigners,
          InitiatingProcessFileName, InitiatingProcessFolderPath
  | order by Timestamp desc
```

### How to Investigate?

1. validate what changed
   - confirm the file path under \AppData\Local\Apps\2.0\ and whether it is a clickonce-style application cache location
   - review whether the event is a create or modify action and how often it occurred
   - compare the current signer value to the historical signer set for that same device and path

2. assess signer-change significance
   - determine if the new signer is unsigned/unknown or a different publisher than expected
   - check whether the previous signer set includes a stable, known vendor and the new signer deviates unexpectedly
   - note if multiple files on the same device switched signers at the same time (batch change vs isolated)

3. review file identity and provenance
   - inspect the SHA1 and whether it is new in your environment
   - check if the file name/path matches a known application update pattern or looks random/unusual
   - verify whether the file appears to be a binary, library, or runtime component consistent with the app

4. investigate the initiating process
   - review which process performed the write and where it executed from (initiating process name and folder path)
   - validate whether the initiator is consistent with clickonce/app deployment behavior or a suspicious scripting/installer process
   - look for initiating process paths in user-writable directories or temp locations

5. correlate with user activity and installs
   - determine which user was active on the device at the time and whether they recently installed/updated software
   - correlate with recent application launches that could trigger clickonce cache refreshes
   - look for concurrent browser/email download activity that could explain a new app deployment

6. scope the pattern across endpoints
   - check whether the same path and new signer appear on multiple devices (suggesting enterprise software rollout or widespread compromise)
   - identify clusters by signer, file name, or initiating process to separate legitimate updates from anomalies
   - note whether the change is limited to a single device/user (targeted) or broadly distributed (campaign or deployment)
