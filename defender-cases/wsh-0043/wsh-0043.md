## WSH-0043 MFA user details added to multiple users

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0043 MFA user details added to multiple users"_ has been created and how to use it.

### Required Access

These hunting cases are linked through a published application that grants us permission to perform threat hunting via the API in our customers' security portals.

### Custom Changes

* No custom changes are made.

## Overview

This usecase looks for MFA user details that have been added to multiple users

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **Identity Protect Cloud** module.

### How to Detect?

The **"CloudAppEvents"** table can be used to hunt for suspicious MFA additions to multiple user accounts. Related activities will be detected with the following KQL query:

### KQL

```kql
    CloudAppEvents
    | where Timestamp > ago(1d)
    | where ActionType == "Update user." and RawEventData contains "StrongAuthenticationUserDetails"
    | extend Target = RawEventData.ObjectId
    | extend Actor = RawEventData.UserId
    | extend reportId= RawEventData.ReportId
    | mvexpand ModifiedProperties = parse_json(RawEventData.ModifiedProperties)
    | where ModifiedProperties.Name == "StrongAuthenticationUserDetails"
    | extend NewValue = parse_json(replace_string(replace_string(tostring(ModifiedProperties.NewValue),"[",""),"]",""))
    | extend OldValue = parse_json(replace_string(replace_string(tostring(ModifiedProperties.OldValue),"[",""),"]",""))
    | mv-expand NewValue
    | mv-expand OldValue
    | where (tostring( bag_keys(OldValue)) == tostring(bag_keys(NewValue))) or (isempty(OldValue) and tostring(NewValue) !contains ":null") or (isempty(NewValue) and tostring(OldValue) !contains ":null") 
    | extend ChangedValue = tostring(bag_keys(NewValue)[0])
    | extend OldValue = tostring(parse_json(OldValue)[ChangedValue])
    | extend NewValue = tostring(parse_json(NewValue)[ChangedValue])
    | extend OldValue = case(ChangedValue == "PhoneNumber" or ChangedValue == "AlternativePhoneNumber", replace_strings(OldValue,dynamic([' ','(',')']), dynamic(['','',''])), OldValue )
    | extend NewValue = case(ChangedValue == "PhoneNumber" or ChangedValue == "AlternativePhoneNumber", replace_strings(NewValue,dynamic([' ','(',')']), dynamic(['','',''])), NewValue )
    | where tostring(OldValue) != tostring(NewValue)
    | extend Action = case(isempty(OldValue), strcat("Added new ",ChangedValue, " to Strong Authentication."),isempty(NewValue),strcat("Removed existing ",ChangedValue, " from Strong Authentication."),strcat("Changed ",ChangedValue," in Strong Authentication."))
    | project Timestamp,Action,Actor,Target,ChangedValue,OldValue,NewValue
    | where isnotempty(NewValue)
    | summarize min(Timestamp),max(Timestamp),make_set(Target) by NewValue
    | extend UserCount = array_length(set_Target)
    | where UserCount > 1
```

## How to Investigate?

1. validate the MFA detail changes
   - identify which authentication attribute was modified (phone number, alternative phone, etc.)
   - review whether the change was an add, remove, or update action
   - confirm that the same new value was applied to multiple user accounts

2. review the actor performing the changes
   - identify the account that made the modifications
   - verify whether this account normally manages authentication settings
   - check for recent role or privilege changes tied to this actor

3. analyze timing and volume
   - review the time window between the first and last change
   - determine if the updates happened rapidly (automation) or manually
   - check how many users were affected in total

4. assess pattern and reuse risk
   - evaluate why the same phone number or authentication value appears across multiple users
   - check if this aligns with any known admin or service account practices
   - identify if this could enable account takeover or MFA bypass scenarios

5. correlate with authentication activity
   - review recent sign-in attempts for affected users
   - check for failed MFA challenges or suspicious login locations
   - look for impossible travel or unfamiliar devices

6. scope for broader impact
   - search for similar authentication changes outside the 24-hour window
   - identify whether other attributes were modified in parallel
   - check if the same actor modified additional security settings
