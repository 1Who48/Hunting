## WSH-0064 EDRChoker Policy-based QoS Throttling of EDR/Security Processes

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0064 EDRChoker Policy-based QoS Throttling of EDR/Security Processes"_ has been created, how to use it.

### Required Access

These hunting cases are linked through a published application that grants us permission to perform threat hunting via the API in our customers' security portals.

## Overview

EDRChoker is an EDR evasion technique that abuses Windows Policy-based Quality of Service (QoS) to silently sever the connection between an EDR agent and its management server, without blocking or dropping packets and without leaving the `packet-block` / `packet-drop` traces produced by Windows Filtering Platform (WFP) tooling such as EDRSilencer. Instead of filtering traffic, the technique creates QoS policies that apply an extremely low outbound bandwidth limit (`ThrottleRateAction`, as low as 8 bits per second) to specific EDR/security process names. At that bandwidth the agent can never complete a TLS handshake — a modern handshake averages 3–6 KB and frequently exceeds 10 KB — so every connection attempt times out, isolating the agent from its server and starving the SOC of telemetry.

The throttling is enforced by the QoS Packet Scheduler (`pacer.sys`), an NDIS lightweight filter driver that sits at the NDIS layer, below WFP and closer to the network card. Because most EDR-blocking tooling operates no deeper than WFP, agents that do not actively inspect QoS policies will be governed by these rules without realising it. The QoS policies are written to the registry, each named with the target process name plus a random GUID, and persist across reboots. EDRChoker creates these policies in two modes: install mode (reads an input file of EDR process names and applies throttling policies) and remove mode (deletes the policies it created). Because legitimate QoS policies exist in many enterprises, this detection focuses on the high-fidelity signal: a QoS policy whose target application matches a known EDR/AV process name, or a throttle rate set to an implausibly low value.

### Attack Chain

| Stage | Binary / Method | Purpose |
|---|---|---|
| QoS Policy Creation | `New-NetQosPolicy` (PowerShell, NetQos module) | Creates a Policy-based QoS policy with `-AppPathNameMatchCondition` targeting an EDR binary and `-ThrottleRateAction...` setting a minimal bandwidth |
| QoS Policy Creation | Direct registry write to QoS policy keys | Creates the QoS policy (and `ThrottleRate` value) directly under the QoS policy store, bypassing the cmdlet |
| Throttle Enforcement | `pacer.sys` (QoS Packet Scheduler, NDIS LWF) | Enforces the bandwidth limit below the WFP layer, causing the agent's outbound traffic to constantly time out |
| Telemetry Isolation | EDR/security agent process (e.g. `MsSense.exe`, `elastic-endpoint.exe`, `CSFalconService.exe`) | Agent loses server connectivity; logs and live response can no longer be collected |
| Persistence | QoS registry policy keys | Policies survive reboot, maintaining the throttle until explicitly removed |

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **DeviceRegistryEvents** module. The **DeviceProcessEvents** module provides additional coverage of the PowerShell-based creation path.

### How to Detect?

This rule detects the creation of Policy-based QoS registry policies whose target application matches a known EDR/AV process name. EDRChoker writes one QoS policy per targeted process, naming each policy with the process name plus a random GUID and setting `ThrottleRateAction` to a minimal value (e.g. 8 bps). The detection matches `RegistryKeyCreated` and `RegistryValueSet` actions under the QoS policy store where the `Application Name` value or the value data references an EDR process. Because exact QoS registry value names and key paths can vary by Windows build and by whether the policy is created in the `ActiveStore` / `PersistentStore` or via Group Policy, the query is deliberately broad on the key path and should be validated against EDRChoker output in a lab before tightening. A companion detection (WSH-0064b) covers implausibly low throttle values; the PowerShell creation path can be corroborated via `DeviceProcessEvents` command lines containing `New-NetQosPolicy` and `ThrottleRateAction`.

### KQL

```kql
   let edrProcesses = dynamic([
       "MsMpEng.exe","MsSense.exe","SenseIR.exe","SenseCncProxy.exe","SenseNdr.exe",
       "elastic-agent.exe","elastic-endpoint.exe","filebeat.exe","winlogbeat.exe",
       "CSFalconService.exe","CSFalconContainer.exe",
       "SentinelAgent.exe","SentinelServiceHost.exe","SentinelStaticEngine.exe",
       "cb.exe","RepMgr.exe","RepUx.exe","cyserver.exe","CylanceSvc.exe",
       "xagt.exe","CarbonBlack.exe","TaniumClient.exe","Traps.exe","cytool.exe"]);
   DeviceRegistryEvents
   | where Timestamp > ago(1d)
   | where ActionType in ("RegistryKeyCreated", "RegistryValueSet")
   | where RegistryKey has @"\QoS"
   | where RegistryValueName =~ "Application Name" or RegistryValueData has_any (edrProcesses)
   | where RegistryValueData has_any (edrProcesses)
   | project Timestamp, DeviceName, DeviceId, RegistryKey, RegistryValueName, RegistryValueData,
             InitiatingProcessFileName, InitiatingProcessCommandLine, InitiatingProcessAccountName
   | sort by Timestamp desc
```

## How to Investigate?

1. **Identify the QoS policy and its target**
   - Review `RegistryKey`, `RegistryValueName`, and `RegistryValueData` to confirm the policy targets an EDR/security binary (`Application Name` value) rather than a legitimate business application
   - Note the policy name in the key path — EDRChoker appends a random GUID to the process name, so a policy named after an EDR process plus a GUID is a strong indicator
   - Determine whether a corresponding `ThrottleRate` value was set and how low it is; values in the range of single-digit bits or bytes per second are not consistent with legitimate QoS

2. **Assess the creating process and account**
   - Review `InitiatingProcessFileName` and `InitiatingProcessCommandLine` to determine how the policy was created (PowerShell `New-NetQosPolicy`, `reg.exe`, a custom binary, or Group Policy client)
   - PowerShell creation containing `New-NetQosPolicy` / `ThrottleRateAction` with an EDR `-AppPathNameMatchCondition` is high suspicion
   - Review `InitiatingProcessAccountName` to determine whether the account has a legitimate administrative reason to manage QoS; EDRChoker requires local Administrator rights to run

3. **Confirm impact on the agent**
   - Check whether the targeted EDR agent on the same `DeviceId` lost server connectivity, stopped reporting, or shows a gap in telemetry around the policy creation time
   - A reporting gap that begins shortly after the QoS policy was created strongly corroborates an active choke

4. **Investigate the account context and preceding activity**
   - Determine whether `InitiatingProcessAccountName` is a local administrator, domain administrator, or service account
   - Check for signs of privilege escalation prior to the policy creation, since Administrator rights are a prerequisite — per the source research, the most reliable detection opportunity is the activity that precedes the attacker gaining admin rights
   - Review logon events for the account (interactive, RDP, or remote execution framework such as PsExec / WMI / WinRM)

5. **Determine scope and whether multiple agents were targeted**
   - EDRChoker is typically run with a list of many EDR process names to cover an unknown environment; check whether multiple QoS policies referencing different EDR/AV processes were created on the same device in the same burst
   - Search for the same pattern of QoS-policy creation across additional devices in the tenant

6. **Check for removal / cleanup**
   - EDRChoker remove mode deletes the policies it created; look for subsequent `RegistryKeyDeleted` events on the same QoS policy keys, which may indicate the attacker restoring state after completing their objective

## How to Respond?

If the incident is identified as a true positive, proceed with standard remediation actions.

### Custom Remediation Actions

* Immediately isolate the affected device from the network to prevent further attacker activity while the EDR agent's telemetry may be unreliable
* Remove the malicious QoS policies after forensic preservation — delete the attacker-created policies (e.g. via `Remove-NetQosPolicy` or by removing the corresponding QoS registry keys) to restore agent connectivity
* Verify the targeted EDR agent has regained connectivity to its management server and is reporting telemetry again
* Audit all Policy-based QoS policies on the affected device and, where feasible, across the tenant, to confirm no additional throttling policies remain
* Investigate how the attacker obtained the local Administrator rights required to create the policies, and remediate the underlying privilege escalation or credential compromise
* Establish ongoing auditing of QoS policy creation (PowerShell audit / script block logging for the NetQos module and Windows Event Log entries for QoS policy changes) so future policy creation is tracked
* Review the device for other EDR-evasion artifacts (WFP filters, driver-based tampering) that may have been deployed alongside the QoS choke
