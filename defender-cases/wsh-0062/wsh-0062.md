## WSH-0062 Malicious Chrome Extension Supply Chain Compromise

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0062 Malicious Chrome Extension Supply Chain Compromise"_ has been created, how to use it.

### Required Access

These hunting cases are linked through a published application that grants us permission to perform threat hunting via the API in our customers' security portals.

### Custom Changes

* No custom changes are made.

## Overview

A threat actor compromised developer accounts to distribute malicious updates to 16 legitimate Chrome extensions via the Chrome Web Store, impacting approximately 3.2 million users. The affected extensions — including ad blockers, emoji keyboards, screen capture tools, and proxy services — were injected with obfuscated service worker scripts that check in with per-extension configuration servers on installation, strip Content Security Policy (CSP) headers to enable cross-site scripting, exfiltrate browsing history and credentials, manipulate search engine results, and inject unauthorized advertisements. The configuration servers resolve to Bunny CDN infrastructure and are backed by DigitalOcean Apps Platform instances sharing a common `x-do-app-origin` header (`978bc8ed-09a8-444b-9142-df5a19366612`). A fallback C2 domain (`c.blipshotextension[.]com`) is hardcoded across all extensions. The campaign was publicly disclosed by GitLab Threat Intelligence on February 13, 2025. Google has since removed the extensions from the Chrome Web Store; however, removal does not trigger automatic uninstallation, meaning affected endpoints may still have the compromised extensions installed.

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **DeviceFileEvents** module.

### How to Detect?

This rule detects the presence of known compromised Chrome extension IDs on managed endpoints by scanning DeviceFileEvents for file activity in browser extension directories matching any of the 16 known malicious extension identifiers. The detection covers a 90-day lookback to account for extensions that may have been installed before public disclosure and have not yet been removed.

### KQL

```kql
    let days_ago = ago(30d); // Set the lookback time for the DeviceFileEvents table. Example: 30d
    let feed_lookback_time = ago(365d); // Set the lookback time for the feed 'insert_date' to avoid old entries. Example: 365d
    // DO NOT EDIT BELOW THIS LINE
    let ExtensionThreatFeed = externaldata(indicators:dynamic)
        // Feed from https://malext.toborrm.com/
        [@"https://raw.githubusercontent.com/toborrm9/malicious_extension_sentry/main/threat-intel-feeds/malext_feed.json"]
        with (format="multijson")
        | mv-expand indicators
        | extend
            feed_insert_date  = todatetime(indicators.insert_date),
            feed_extension_id = tostring(indicators.extension_id),
            feed_ext_name     = tostring(indicators.name),
            feed_store_url    = tostring(indicators.chrome_store_url),
            feed_source       = tostring(indicators.source)
        | where feed_insert_date > feed_lookback_time
        | project feed_insert_date, feed_extension_id, feed_ext_name, feed_store_url, feed_source;
    DeviceFileEvents
    | where Timestamp > days_ago
    | where ActionType in~ ("FileCreated", "FileModified", "FileRenamed")
    // Below file paths only tested on Windows
    // Chrome path ...\Google\Chrome\User Data\<Profile>\Extensions\<extension_id>\...
    // Edge path ...\Microsoft\Edge\User Data\<Profile>\Extensions\<extension_id>\...
    | where FolderPath has_any ("Google\\Chrome\\User Data", "Microsoft\\Edge\\User Data") and FolderPath has @"\Extensions\"
    // Extract the WxtensionId after the "\Extensions\" FolderPath
    | extend ExtensionId = tolower(extract(@"\\Extensions\\([a-z]{32})\\", 1, FolderPath))
    | where isnotempty(ExtensionId)
    | join kind=inner ExtensionThreatFeed on $left.ExtensionId == $right.feed_extension_id
    | project Timestamp, feed_insert_date, feed_extension_id, feed_ext_name, DeviceId, DeviceName, InitiatingProcessAccountUpn, ActionType, FileName, FolderPath, ExtensionId, feed_store_url, feed_source
    | sort by Timestamp desc
```

## How to Investigate?

1. **Identify the matched extension**
   - Review the `MatchedId` field to determine which compromised extension was detected
   - Cross-reference with the Targeted Extensions table to identify the extension name and its associated C2 configuration domain
   - Use `Timestamp` and `DeviceName` to establish when and where the activity occurred

2. **Determine extension status**
   - Check whether the extension is still installed and active on the device
   - Review `ActionType` to understand if the file event represents an installation, update, or runtime activity
   - Check if the extension version corresponds to a known malicious update

3. **Investigate the initiating process**
   - Review `InitiatingProcessFileName` and `InitiatingProcessCommandLine` to determine what triggered the file activity
   - Legitimate activity would typically originate from `chrome.exe` or a browser update process
   - Anomalous parent processes may indicate additional compromise

4. **Assess data exposure**
   - Determine what data the user may have accessed while the compromised extension was active
   - Review browsing history for sensitive sites (banking, corporate SSO portals, email) visited during the exposure window
   - Identify whether autofill or saved credentials may have been exfiltrated

5. **Check for network indicators**
   - Search `DeviceNetworkEvents` for outbound connections to known C2 configuration domains associated with the matched extension
   - Look for connections to the fallback domain `c.blipshotextension[.]com`
   - Check for connections to infrastructure hosted on Bunny CDN or DigitalOcean Apps Platform with the `x-do-app-origin` header value `978bc8ed-09a8-444b-9142-df5a19366612`

6. **Assess scope across the environment**
   - Determine whether the same extension is present on additional devices across the tenant
   - Identify whether the compromised extension was deployed via enterprise policy or installed individually by users
   - Check whether multiple compromised extensions from this campaign are present on the same device, which may indicate broader exposure

## How to Respond?

If the incident is identified as a true positive, proceed with standard remediation actions.

### Custom Remediation Actions

* Remove the compromised extension from all affected browsers — note that Chrome Web Store removal does not trigger automatic uninstallation
* Revoke and rotate credentials for any accounts accessed via the browser while the compromised extension was active, prioritising cloud provider consoles, CI/CD platforms, corporate SSO, and email
* Block known C2 configuration domains at the perimeter firewall and DNS filtering layer, including: `blipshotextension[.]com`, `emojikeyboardextension[.]com`, `watoolkit[.]com`, `colorchanger[.]net`, `ytvideoeffectsextension[.]com`, `themesforytextension[.]com`, `adblockforytextension[.]com`, `pagerefresh-extension[.]com`, `wistiaextension[.]com`, `sdmextension[.]com`, `emojikeyboardforchrome[.]com`, `noadsadblocker[.]com`, `abu-xt[.]com`, `abfc-extension[.]com`, `nimblecapture[.]com`, `kproxyservers[.]site`
* Audit browser extension policies to restrict installation to an approved allowlist where possible
* Invalidate any active browser sessions on affected devices to terminate potentially hijacked sessions
