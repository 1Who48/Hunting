## WSH-0058 The Second Coming: How Sha1-Hulud Infiltrated the npm Ecosystem

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0058 The Second Coming: How Sha1-Hulud Infiltrated the npm Ecosystem"_ has been created, how to use it.

### Required Access

These hunting cases are linked through a published application that grants us permission to perform threat hunting via the API in our customers' security portals.

### Custom Changes

* No custom changes are made.

## Overview

Sha1-Hulud — often referred to as “The Second Coming” — is a major supply-chain attack targeting the npm ecosystem. Attackers managed to compromise more than 800 legitimate npm packages, including widely used projects such as Zapier, ENS Domains, PostHog, and Postman, replacing them with malicious trojanized versions.

The attack is triggered during the “pre-install” phase, where an embedded script downloads the Bun runtime and executes a payload designed to steal developer credentials, authentication tokens, and other sensitive secrets. If the malware cannot steal credentials or establish persistence, it escalates by attempting destructive actions — including deleting all writable files within the user’s home directory.

To maintain access, the attackers also abuse legitimate developer infrastructure by secretly installing a GitHub Actions runner inside the victim’s account, giving them remote code execution through publicly accessible GitHub Discussions.

The scope is massive, with tens of thousands of GitHub repositories already confirmed or suspected to be compromised.

### MITRE ATT&CK

This attack tactic can be mapped on the MITRE ATT&CK framework:

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **DeviceFileEvents** module.

### How to Detect?

* Monitor for unexpected pre-install script executions within npm packages, especially those downloading external runtimes like Bun. Audit recent package updates for suspicious version changes or unfamiliar maintainers. Look for unauthorized GitHub Actions runners, unusual access tokens being created, or outbound network requests during package installation. Alert on file-system operations targeting large portions of the home directory and any sudden mass-deletion attempts. Regularly scan developer machines and CI pipelines for anomalous processes or unknown binaries introduced by compromised dependencies.

### KQL

```kql
    let lookback = 7d;
    // IOCs for malicious files associated with the campaign
    let malicious_hashes = dynamic([
        "a3894003ad1d293ba96d77881ccd2071446dc3f65f434669b49b3da92421901a", // setup_bun.js
        "62ee164b9b306250c1172583f138c9614139264f889fa99614903c12755468d0", // bun_environment.js
        "f099c5d9ec417d4445a0328ac0ada9cde79fc37410914103ae9c609cbc0ee068", // bun_environment.js
        "cbb9bc5a8496243e02f3cc080efbe3e4a1430ba0671f2e43a202bf45b05479cd"  // bun_environment.js
    ]);
    let malicious_filenames = dynamic(["setup_bun.js", "bun_environment.js"]);
    // Part 1: Detect malicious file creation by hash or name
    let file_indicators =
    DeviceFileEvents
    | where Timestamp > ago(lookback)
    | where ActionType == "FileCreated"
    | where SHA256 in (malicious_hashes)
        // FP Note: Searching by filename can be prone to FPs. This is scoped to paths containing ".npm" to reduce noise.
        or (FileName in (malicious_filenames) and FolderPath contains ".npm")
    | extend Activity = "Malicious File Drop (Sha1-Hulud)", Tactic = "Execution", Technique = "T1204.002";
    // Part 2: Detect malicious preinstall script execution
    let process_indicators_preinstall =
    DeviceProcessEvents
    | where Timestamp > ago(lookback)
    | where ProcessCommandLine has "node" and ProcessCommandLine has "setup_bun.js"
    | extend Activity = "Malicious NPM Preinstall Script (Sha1-Hulud)", Tactic = "Execution", Technique = "T1059.007";
    // Part 3: Detect GitHub Actions persistence mechanism
    let persistence_indicators =
    DeviceFileEvents
    | where Timestamp > ago(lookback)
    | where ActionType == "FileCreated"
    // Look for the specific workflow file used for C2 or the runner installation in the hidden directory.
    // FP Note: Legitimate use of 'discussion.yaml' in a workflow or a '.dev-env' directory is possible but unlikely in this combination.
    | where (FolderPath has_all (".github", "workflows") and FileName =~ "discussion.yaml")
        or (FolderPath contains "/.dev-env/" and FileName has_any ("run.sh", "config.sh"))
    | extend Activity = "GitHub Actions Persistence (Sha1-Hulud)", Tactic = "Persistence", Technique = "T1543.002";
    // Part 4: Detect destructive commands used as a fallback
    let destructive_commands =
    DeviceProcessEvents
    | where Timestamp > ago(lookback)
    // Linux destructive command
    | where (FileName =~ "bash" and ProcessCommandLine has "find" and ProcessCommandLine has "$HOME" and ProcessCommandLine has "shred" and ProcessCommandLine has "xargs" and ProcessCommandLine has "delete")
    // Windows destructive command
    or (InitiatingProcessFileName =~ "cmd.exe" and ProcessCommandLine has_all ("del", "/F", "/Q", "/S", "rd", "%USERPROFILE%"))
    | extend Activity = "Destructive Command (Sha1-Hulud)", Tactic = "Impact", Technique = "T1485";
    // Union all indicators and summarize by device and user
    union file_indicators, process_indicators_preinstall, persistence_indicators, destructive_commands
    | summarize
        StartTime = min(Timestamp),
        EndTime = max(Timestamp),
        AllActivities = make_set(Activity, 10),
        Tactics = make_set(Tactic, 10),
        Techniques = make_set(Technique, 10),
        FileNames = make_set(FileName),
        FileHashes = make_set(SHA256),
        CommandLines = make_set(ProcessCommandLine),
        InitiatingCommandLines = make_set(InitiatingProcessCommandLine)
        by DeviceId, DeviceName, AccountName, AccountDomain, bin(Timestamp, 1h)
    | extend Host = iif(isnotempty(AccountDomain), strcat(AccountDomain, "\\", AccountName), AccountName)
    | project-away DeviceId, AccountName, AccountDomain, Timestamp
```

## How to Investigate?

1. validate which indicator(s) triggered per host and hour
   - review the activities list to see whether this is a file drop, preinstall execution, github actions persistence, and/or destructive commands
   - confirm the first and last seen timestamps and whether events cluster tightly (single incident) or recur (ongoing activity)
   - check whether multiple tactics appear together (execution + persistence + impact), which strongly increases confidence

2. investigate the npm-related file drops
   - confirm whether the match was by sha256 (high confidence) or by filename in a .npm path (higher false-positive risk)
   - identify the exact file path and whether it aligns with npm cache/project structures on that endpoint
   - trace how the file arrived on disk by reviewing the creating process and any adjacent archive extraction or download activity

3. analyze the node preinstall execution chain
   - inspect the node command line that references setup_bun.js to determine the working directory and associated package context
   - identify the parent process that launched node (npm/yarn/pnpm, CI runner, IDE, terminal) and whether it looks interactive or automated
   - correlate execution timing with package installation events (dependency install bursts, new lockfile changes, build steps)

4. review github actions persistence artifacts
   - validate whether a new workflow file (discussion.yaml) appeared under .github/workflows and whether that repo path is expected on the device
   - check for creation of /.dev-env/ scripts (run.sh, config.sh) and whether they map to runner installation or hidden execution tooling
   - correlate these file creations with subsequent process executions that reference the same directories or scripts

5. assess destructive command evidence
   - determine whether the command line matches linux shredding behavior targeting $HOME or windows deletion behavior targeting %USERPROFILE%
   - review timing relative to other indicators to see if destructive activity followed failed persistence/execution
   - check whether the commands appear complete and purposeful versus partial strings from logs or benign maintenance scripts

6. scope by user, project, and repeat indicators
   - review the host field (domain\user) to understand which identities are involved and whether the same user appears across multiple devices
   - compare filenames, hashes, and command lines across results to identify common staging paths, repeated payload names, or shared automation
   - look for patterns suggesting a supply-chain event (same npm artifacts across many hosts) versus a single compromised developer workstation
