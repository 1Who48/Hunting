## WSH-0059 Fake BSOD MSBuild Malware Detection

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0059 Fake BSOD MSBuild Malware Detection"_ has been created, how to use it.

### Required Access

These hunting cases are linked through a published application that grants us permission to perform threat hunting via the API in our customers' security portals.

### Custom Changes

* No custom changes are made.

## Overview

This query detects behavior linked to the PHALT#BLYX malware campaign by correlating process, file, and network activity across a 1-day period. It focuses on PowerShell droppers, abuse of msbuild.exe for proxy execution, Microsoft Defender tampering, malicious file drops, startup persistence, and command-and-control traffic over port 3535. The goal is to identify devices showing multiple stages of the attack chain rather than isolated indicators, enabling higher-confidence threat hunting and incident response.

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **DeviceFileEvents** module.

### How to Detect?

This detection works by correlating multiple telemetry sources in Microsoft Defender for Endpoint to identify the full PHALT#BLYX attack chain. It monitors process activity for suspicious PowerShell usage and abuse of trusted Windows tools like msbuild.exe, which attackers use to proxy malicious execution.

It also tracks file system events to catch known payloads and persistence artifacts dropped in sensitive locations such as ProgramData, Temp, and the Startup folder. In parallel, the query inspects network traffic for connections to known command-and-control infrastructure and abnormal use of port 3535.

Rather than relying on single indicators, the detection aggregates these behaviors per device. Systems that exhibit multiple stages of the intrusion—execution, defense evasion, persistence, and beaconing—are flagged, enabling high-confidence identification of compromised endpoints.

### KQL

```kql
   let Timeframe = 1d;
   let SuspiciousPaths = dynamic([ @"\\ProgramData\\v.proj", @"\\ProgramData\\staxs.exe", @"\\ProgramData\\pins.dat", @"\\Windows\\Temp\\tybd7.exe", @"\\Startup\\DeleteApp.url", @"\\Startup\\update.lnk" ]);
   let ProcSignals = materialize( DeviceProcessEvents 
   | where Timestamp > ago(Timeframe)
   | where ( FileName in~ ("powershell.exe","pwsh.exe") and ( (ProcessCommandLine has_all ("gci", @"C:\\","-filter","msbuild.exe","-r")) or (ProcessCommandLine has_any ("iwr","Invoke-WebRequest") and ProcessCommandLine has "2fa-bns.com" and ProcessCommandLine has "v.proj") or (ProcessCommandLine has "msbuild" and ProcessCommandLine has "v.proj") ) ) or (FileName =~ "msbuild.exe" and ProcessCommandLine has "v.proj") or (ProcessCommandLine has_any ("Add-MpPreference","Set-MpPreference") and ProcessCommandLine has_any ("ExclusionPath","ExclusionExtension","DisableRealtimeMonitoring")) or (ProcessCommandLine has "Start-BitsTransfer" and ProcessCommandLine has "2fa-bns.com")
   | extend SignalType = case( FileName in~ ("powershell.exe","pwsh.exe"), "PowerShellDropperOrStager", FileName =~ "msbuild.exe", "MSBuildProxyExecution", ProcessCommandLine has "Add-MpPreference", "DefenderExclusion", ProcessCommandLine has "Set-MpPreference", "DefenderRealtimeDisable", ProcessCommandLine has "Start-BitsTransfer", "BITSDownload", "Other" )
   | project Timestamp, DeviceName, DeviceId, AccountName, InitiatingProcessAccountName, FileName, ProcessCommandLine, InitiatingProcessFileName, InitiatingProcessCommandLine, SignalType, ReportId );
   // Scalar guard: return nothing unless ProcSignals has at least 1 row
   let HasProcSignals = toscalar(ProcSignals | summarize c=count());
   // Keys we use to tie FileSignals to a matching ProcSignals-causing process on the same device
   let ProcKeys = materialize( ProcSignals | project DeviceId, ProcTimestamp=Timestamp, ProcFileName=FileName, ProcCmd=ProcessCommandLine, ProcSignalType=SignalType, ProcReportId=ReportId );
   let FileSignals = DeviceFileEvents | where Timestamp > ago(Timeframe)
   | where FolderPath has_any (SuspiciousPaths) or FileName in~ ("v.proj","staxs.exe","tybd7.exe","pins.dat","DeleteApp.url","update.lnk")
   // Only keep file events created by a process that appears in ProcSignals (same device + same initiating process cmdline/name), 
   // and (optionally) close in time to that ProcSignals row. 
   | join kind=innerunique (ProcKeys) on DeviceId
   | where InitiatingProcessFileName =~ ProcFileName and InitiatingProcessCommandLine == ProcCmd
   | where Timestamp >= datetime_add("minute", -10, ProcTimestamp) and Timestamp <= datetime_add("hour", 2, ProcTimestamp)
   | extend SignalType = case( FolderPath has @"\\ProgramData\\" and FileName =~ "v.proj", "DroppedMSBuildProject(v.proj)", FolderPath has @"\\ProgramData\\" and FileName =~ "staxs.exe", "DroppedLoader(staxs.exe)", FolderPath has @"\\Windows\\Temp\\" and FileName =~ "tybd7.exe", "TempCopy(tybd7.exe)", FolderPath has @"\\Startup\\" and FileName =~ "DeleteApp.url", "StartupPersistence(DeleteApp.url)", FolderPath has @"\\Startup\\" and FileName =~ "update.lnk", "StartupPersistence(update.lnk)", FolderPath has @"\\ProgramData\\" and FileName =~ "pins.dat", "InfectionMarker(pins.dat)", "FileArtifact" )
   | project Timestamp, DeviceName, DeviceId, InitiatingProcessAccountName, ActionType, FolderPath, FileName, SHA256, InitiatingProcessFileName, InitiatingProcessCommandLine, SignalType, ReportId, MatchedProcSignalType=ProcSignalType, MatchedProcReportId=ProcReportId, MatchedProcTimestamp=ProcTimestamp;
   union ProcSignals, FileSignals 
   | where HasProcSignals > 0 
   | sort by DeviceName asc, Timestamp asc 
   | summarize FirstSeen=min(Timestamp), LastSeen=max(Timestamp), SignalCount=count(), SignalTypes=make_set(SignalType, 50), ExampleCommands=make_set_if(ProcessCommandLine, isnotempty(ProcessCommandLine), 10), ExampleFiles=make_set_if(strcat(FolderPath, @"\\", FileName), isnotempty(FileName), 10) by DeviceName, DeviceId
   | order by LastSeen desc
```

## How to Investigate?

1. validate which signals fired on each device
   - review the signal types to see if this is powershell staging, msbuild proxy execution, defender setting changes, bits download, and/or specific file artifacts
   - compare first seen and last seen to understand duration and whether activity repeats
   - prioritize devices where both process signals and file signals appear together

2. analyze the powershell and execution patterns
   - review example commands for web retrieval behavior (invoke-webrequest, bits transfer) and staging references to v.proj
   - check for msbuild discovery commands (searching for msbuild.exe) as an execution-prep indicator
   - validate whether commands show obfuscation or indirect execution patterns

3. investigate msbuild proxy execution behavior
   - confirm msbuild.exe executions reference v.proj and identify where v.proj was located
   - review the initiating process chain to see what launched msbuild and whether it originated from powershell
   - assess whether msbuild usage is normal on that endpoint (developer/build host) or unexpected

4. review defender setting manipulation signals
   - inspect commands indicating exclusion creation or realtime monitoring disable attempts
   - correlate those events with the rest of the sequence to understand if defense weakening preceded payload execution
   - identify whether multiple such commands occurred in quick succession (automation)

5. examine file artifacts and staging locations
   - review example files to confirm presence of v.proj, staxs.exe, tybd7.exe, and pins.dat in the listed directories
   - correlate file timestamps with initiating process details to identify what dropped or modified each artifact
   - pay close attention to startup items (DeleteApp.url, update.lnk) as indicators of persistence attempts and when they appeared

6. reconstruct the per-device timeline
   - build a chronological sequence: initial powershell/bits activity → file drops (v.proj/staxs/pins/tybd7) → msbuild execution → startup artifact creation
   - identify whether the chain is complete or partial (e.g., file drops without msbuild, or msbuild without downloads)
   - compare patterns across devices to determine if this is a common playbook or isolated behavior
