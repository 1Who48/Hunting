## WSH-0016 Shell command for firewall(RDP)

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0016 Shell command for firewall(RDP)"_ has been created, how to use it.

## Overview

The following query will detect Network Shell command for firewall to allow incoming RDP connections

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **Device Protect** module.

### How to Detect?

The **"DeviceProcessEvents"** we can hunt on this application what attackers enable RDP via the command shell.

### KQL

```kql
    let Timeframe = 1d; // Choose the best timeframe for your investigation
    let fwcommands = dynamic([@"advfirewall", @"firewall", @"add rule", @"dir=in", @"localport=3389", @"action=allow"]);
    DeviceProcessEvents
    | where Timestamp > ago(Timeframe)
    | where FileName has @"netsh.exe"
    | where ProcessCommandLine has_all (fwcommands)
    | where ActionType has "ProcessCreated"
    | project DeviceId, DeviceName, ProcessCommandLine
```

## How to Investigate?

1. Validate administrative intent
    * Confirm whether the firewall rule change was part of an approved change, troubleshooting effort, or remote access request.
    * Identify the user or service account responsible and verify change management or ticketing records.

2. Assess exposure created
    * Enabling inbound RDP significantly increases attack surface—determine whether the rule applies broadly (any IP) or is scoped to trusted sources.
    * Check whether the system was previously hardened or intentionally restricted from RDP access.

3. Review execution context
    * Analyze the parent process and execution method to see whether netsh.exe was launched interactively, via script, or through a malicious binary.
    * Look for execution from unexpected processes, scheduled tasks, or post-exploitation tooling.

4. Correlate with authentication activity
    * Investigate whether RDP logons occurred shortly after the firewall rule was added, especially from unfamiliar IP addresses or locations.
    * Look for brute-force attempts, successful logons, or MFA bypass indicators following the rule change.

5. Check for persistence or follow-on actions
    * Determine whether additional firewall rules, user accounts, or remote access mechanisms were configured afterward.
    * Review system changes such as service modifications, credential dumping activity, or lateral movement attempts.
