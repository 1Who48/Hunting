## WSH-0052 Using EDR-Redir To Break EDR Via Bind Link and Cloud Filter

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0052 Using EDR-Redir To Break EDR Via Bind Link and Cloud Filter"_ has been created, how to use it.

### Required Access

These hunting cases are linked through a published application that grants us permission to perform threat hunting via the API in our customers' security portals.

### Custom Changes

* No custom changes are made for this Hunt.

## Overview

The post shows how EDR-Redir abuses two Windows mini-filter drivers to neuter or hijack EDRs:

Bind Filter (bindflt.sys) creates a bind link so an EDR’s executable folder is transparently redirected to a folder the attacker controls. With control of that folder, the attacker can drop DLLs/exes, or leave it empty to break the EDR.
Cloud Filter (cldflt.sys / CFAPI) registers a bogus sync root on the EDR’s folder so the product can’t access its own files, effectively isolating or disabling it; this persists across reboots.

The author demonstrates success against Elastic Defend and Sophos Intercept X using bind links, and shows Windows Defender can be blocked via the Cloud Filter trick. Persistence notes and limitations are discussed. Detection is hard because the manipulation occurs at the minifilter level (little user-mode telemetry).

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **DeviceRegistryEvents**, **DeviceFileEvents** and **DeviceTvmInfoGathering** modules.

### How to Detect?

Rather than alerting on the *symptom* (Defender reporting as passive / EDR Block, which is a normal state on devices where Defender is not the primary AV and was the source of vague false positives), this detection triggers on the *technique* itself and uses the Defender AV mode only as enrichment:

* **Cloud Filter variant** — a Cloud Files sync root registered on a Defender directory. This is written under `SyncRootManager` in the registry by `CfRegisterSyncRoot` (cldapi.dll) and persists across reboots, making it the strongest and most specific signal.
* **Bind Link variant** — a non-Microsoft process dropping an executable/script (DLL-hijack payload) inside the Defender directories. Known-good Defender/MDE writers (e.g. `sensecm.exe`, `MsMpEng.exe`) are suppressed via the allow-lists at the top of the query.

The `AvMode` value from **DeviceTvmInfoGathering** is joined as context only — it is not used to gate results.

> **Note:** `AvMode` values are `0` = Active, `1` = Passive, `4` = EDR Block. EDR Block is a legitimate state when Defender is not the primary AV, so it must not be used as a standalone detection trigger.

### KQL

```kql
    // Detection: Detection EDR-Redir for Microsoft Defender for Endpoint
    // Reference: https://www.zerosalarium.com/2025/10/DR-Redir-Break-EDR-Via-BindLink-Cloud-Filter.html
    //
    let LookBack = 1d;
    let DefenderDirIndicators = dynamic(["Windows Defender","Microsoft Defender","Windows Defender\\Platform"]);
    let TrustedInitiators = dynamic([
        "MsMpEng.exe","MsSense.exe","SenseCM.exe","sensecm.exe","SenseCncProxy.exe",
        "SenseIR.exe","SenseNdr.exe","SenseSampleUploader.exe","SenseTVM.exe",
        "MpCmdRun.exe","NisSrv.exe","MpDefenderCoreService.exe","MpDlpService.exe",
        "smartscreen.exe","MsMpEngCP.exe","TiWorker.exe","TrustedInstaller.exe","MoUsoCoreWorker.exe"
    ]);
    let TrustedInitiatorFolders = dynamic([
        "\\Program Files\\Windows Defender",
        "\\ProgramData\\Microsoft\\Windows Defender\\Platform",
        "\\Program Files\\Microsoft Defender"
    ]);
    let SuspiciousExtensions = dynamic([".dll",".exe",".sys",".ps1",".bat",".cmd",".com",".scr"]);
    let CloudFilterAbuse =
        DeviceRegistryEvents
        | where Timestamp > ago(LookBack)
        | where RegistryKey has "SyncRootManager"
        | where RegistryValueData has_any (DefenderDirIndicators)
        | extend Technique = "CloudFilter sync-root registered on Defender folder"
        | project Timestamp, DeviceName, Technique, ActionType, RegistryKey, RegistryValueData,
                  InitiatingProcessAccountName, InitiatingProcessFileName,
                  InitiatingProcessCommandLine, InitiatingProcessFolderPath;
    let FolderTampering =
        DeviceFileEvents
        | where Timestamp > ago(LookBack)
        | where FolderPath has_any (dynamic([
                "\\ProgramData\\Microsoft\\Windows Defender",
                "\\Program Files\\Windows Defender"]))
        | where ActionType in ("FileCreated","FileRenamed")
        | where isnotempty(InitiatingProcessFileName)
        | where not(InitiatingProcessFileName in~ (TrustedInitiators))
        | where not(InitiatingProcessFolderPath has_any (TrustedInitiatorFolders))
        | where not(InitiatingProcessVersionInfoCompanyName has "Microsoft")
        | extend FileExt = tolower(strcat(".", tostring(split(FileName, ".")[-1])))
        | where FileExt in (SuspiciousExtensions)
        | extend Technique = "Non-Microsoft executable dropped inside Defender folder"
        | project Timestamp, DeviceName, Technique, ActionType, FolderPath, FileName,
                  InitiatingProcessAccountName, InitiatingProcessFileName,
                  InitiatingProcessCommandLine, InitiatingProcessFolderPath;
    let TechniqueHits = union CloudFilterAbuse, FolderTampering;
    let AvState =
        DeviceTvmInfoGathering
        | where Timestamp > ago(LookBack)
        | extend AvMode = tostring(parse_json(AdditionalFields).AvMode)
        | summarize arg_max(Timestamp, AvMode) by DeviceName
        | extend AvModeText = case(AvMode == "0","Active",
                                   AvMode == "1","Passive",
                                   AvMode == "4","EDR Block",
                                   strcat("Other(", AvMode, ")"));
    TechniqueHits
    | join kind=leftouter AvState on DeviceName
    | project Timestamp, DeviceName, Technique, ActionType,
              RegistryKey, RegistryValueData, FolderPath, FileName,
              InitiatingProcessAccountName, InitiatingProcessFileName,
              InitiatingProcessCommandLine, InitiatingProcessFolderPath,
              AvModeText
    | sort by Timestamp desc
```

## How to Investigate?

1. identify which technique fired
   - check the `Technique` column: a `CloudFilter sync-root` hit (DeviceRegistryEvents) is high fidelity and persists across reboots; a `Non-Microsoft executable dropped` hit (DeviceFileEvents) indicates a possible Bind Link DLL-hijack payload
   - note the `DeviceName` and `Timestamp` to anchor the rest of the investigation

2. validate the Cloud Filter sync-root registration (if applicable)
   - inspect `RegistryKey` and `RegistryValueData` to confirm a sync root was registered against a Defender directory
   - confirm the initiating process (`InitiatingProcessFileName` / `InitiatingProcessFolderPath`) is not a legitimate cloud-sync provider such as OneDrive
   - because this persists across reboots, treat a confirmed hit as an active persistence mechanism

3. validate the dropped executable context (if applicable)
   - confirm the file truly resides under `ProgramData\Microsoft\Windows Defender` or `Program Files\Windows Defender` via `FolderPath`
   - confirm the initiating process is not a legitimate Defender component and is not on the allow-list
   - inspect the file’s metadata (file name, extension, version info) and determine which process dropped it

4. assess the Defender operational mode (enrichment)
   - review the joined `AvModeText` value as supporting context — Active, Passive, or EDR Block
   - remember EDR Block / Passive can be legitimate on its own; only treat it as relevant when it correlates with a technique hit on the same device
   - correlate the timing of any mode change with the registry/file event timeline

5. review process lineage
   - identify the parent process that launched the initiating process
   - check if execution originated from powershell, cmd, scheduled task, or service
   - determine whether execution was interactive or automated

6. correlate with security telemetry
   - check for gaps in Defender alerts or service health after the technique hit
   - review if other security services were stopped or altered
   - look for parallel attempts to disable logging or tamper with protections

7. scope similar behavior
   - search for the same sync-root registration or dropped file name across other devices
   - check if multiple endpoints show the same technique hits
   - identify patterns indicating automated exploitation or targeted activity
