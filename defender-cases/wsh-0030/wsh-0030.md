## WSH-0030 high risk sign-in activity and have created a resource group

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0030 high risk sign-in activity and have created a resource group"_ has been created, how to use it.

### Required Access

These hunting cases are linked through a published application that grants us permission to perform threat hunting via the API in our customers' security portals.

### Custom Changes

* No custom changes are made.

## Overview

Hunt for users who have high risk sign-in activity, according to AAD Identity Protection, and have created a resource group

### MITRE ATT&CK

This attack tactic can be mapped on the MITRE ATT&CK framework:

| Tactic                | Techniques |
|-----------------------|------------|
| Impact                | T1496      |

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **Device Protect** module.

### How to Detect?

Detects users who have high risk sign-in activity, according to AAD Identity Protection, and have created a resource group in the **"CloudAppEvents"** and **"AADSignInEventsBeta"** table

### KQL

```kql
    let riskyAzureSignIns = (
    AADSignInEventsBeta
    | where Timestamp > ago(1d)
    | where ErrorCode == 0
    | where Application == "Azure Portal"
    | where RiskLevelAggregated == 100 or RiskLevelDuringSignIn == 100
    | project AccountObjectId, RiskySignInTimestamp = Timestamp);
    let resourceGroupCreation = ( 
    CloudAppEvents
    | where Timestamp > ago(1d)
    | where Application == "Microsoft Azure"
    | where ActionType == "Write ResourceGroup"
    | project AccountObjectId, ResourceGroupCreation = Timestamp);
    //join the tables
    riskyAzureSignIns
    | join resourceGroupCreation on AccountObjectId 
    | where ResourceGroupCreation between (RiskySignInTimestamp .. (RiskySignInTimestamp + 12h))
```

## How to Investigate?

1. Validate the risky sign-in
   - Confirm why Azure classified the login as high risk (impossible travel, unfamiliar device, TOR/VPN, malware-linked IP)
   - Review source IP, geo-location, device details, and MFA status
   - Verify with the user if the sign-in was legitimate

2. Review the account’s privilege level
   - Identify assigned roles (Owner, Contributor, custom RBAC)
   - Determine scope of access (subscription, tenant, management group)
   - Flag high-impact permissions that allow resource creation

3. Analyze the resource group creation
   - Review naming conventions, region, and subscription used
   - Identify what resources were deployed inside the group
   - Look for suspicious workloads (VMs, crypto miners, automation scripts)

4. Correlate with additional Azure activity
   - Check for VM creation, NSG rule changes, role assignments
   - Look for Key Vault access, storage accounts, or automation runbooks
   - Review activity timeline for rapid follow-on actions

5. Assess persistence and backdoor risk
   - Hunt for new service principals or API credentials
   - Check for managed identities or scheduled automation jobs
   - Validate if security settings or CA policies were modified

6. Containment and remediation
   - Reset password and revoke active sessions
   - Remove malicious resources and review billing impact
   - Enforce stronger conditional access and MFA policies
