## WSH-0032 Hunt for disabling Defender Antivirus and Defender for Endpoint

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0032 Hunt for disabling Defender Antivirus and Defender for Endpoint"_ has been created, how to use it.

### Required Access

These hunting cases are linked through a published application that grants us permission to perform threat hunting via the API in our customers' security portals.

### Custom Changes

* No custom changes are made.

## Overview

Hunt for disabling activities for Microsoft Defender Antivirus and Microsoft Defender for Endpoint.

### MITRE ATT&CK

This attack tactic can be mapped on the MITRE ATT&CK framework:

| Tactic                | Techniques |
|-----------------------|------------|
| Privilege Escalation  | T1558      |

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **Device Protect** module.

### How to Detect?

Detects activities of disabling for Microsoft Defender Antivirus and Microsoft Defender for Endpoint in the **"DeviceNetworkEvents"** table

### KQL

```kql
    DeviceEvents
    | where Timestamp > ago(1d)
    | where ActionType == "OtherAlertRelatedActivity"
    | where AdditionalFields has "net stop Sense"
    or AdditionalFields has "sc stop Sense"
    or AdditionalFields has "net stop WinDefend"
    or AdditionalFields has "sc stop WinDefend"
    | extend Command = split(AdditionalFields, 'line')[1]
    | project-reorder Timestamp, DeviceId, DeviceName, Command
```

## How to Investigate?

1. Validate the command execution
   - Review the extracted command to confirm which service stop command was used
   - Distinguish between Defender (WinDefend) and EDR (Sense) targeting
   - Check if the syntax matches known admin scripts or attack techniques

2. Identify the executing account
   - Determine which user or service account ran the command
   - Check if the account has local admin or SYSTEM privileges
   - Verify whether the account normally performs security service management

3. Analyze process lineage
   - Identify the parent process that launched the stop command
   - Look for suspicious origins such as PowerShell, cmd, wmic, remote tools
   - Check if the command was part of a script or batch execution

4. Review event timing and frequency
   - Check if multiple stop attempts occurred in a short timeframe
   - Correlate timing with other suspicious activity on the device
   - Identify if this aligns with login events or privilege changes

5. Correlate with security telemetry gaps
   - Check for missing alerts or telemetry immediately after the event
   - Look for logging disruptions or service restarts
   - Validate if other security services were impacted

6. Hunt for related suspicious behavior
   - Look for backup deletion, shadow copy tampering, or log clearing
   - Check for lateral movement or credential access attempts
   - Review file creation and network activity following the event
