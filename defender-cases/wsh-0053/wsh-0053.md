## WWSH-0053 macOS User added to Admin Group

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0053 macOS User added to Admin Group"_ has been created, how to use it.

### Custom Changes

## Overview

This detection monitors for instances where a user is added to the local admin group on a macOS system using either the dscl or dseditgroup command-line utilities. Both tools are native to macOS and are commonly used for managing local users and groups. While system administrators and MDM (Mobile Device Management) solutions may legitimately use these commands, attackers can also abuse them to escalate privileges and gain persistent administrative access.

The query focuses on identifying these potentially risky operations while reducing false positives by allowing legitimate MDM processes (such as jamfmanager) through a whitelist.

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **DeviceProcessEvents** module.

### How to Detect?

The detection begins by defining a whitelist of known legitimate administrative processes or service accounts, stored in the variable legitimAdmin. This list typically includes trusted Mobile Device Management (MDM) agents such as jamfmanager, which are authorized to perform administrative tasks on managed macOS systems. By doing so, the query minimizes false positives by allowing these legitimate processes to carry out expected account management actions without triggering alerts.

Once the trusted list is defined, the detection focuses on identifying unauthorized privilege escalations. The first component of the query examines process creation events in the DeviceProcessEvents table to identify executions of the dscl binary. It specifically looks for command-line arguments that contain the sequence -append, /Groups/admin, and GroupMembership. This combination of arguments is a strong indicator that a user has been added to the local admin group using the dscl utility. When such activity is detected, the query labels the event with the activity description “User Added To Admin Group Via dscl.”

The second component of the detection targets the dseditgroup utility, another macOS command-line tool capable of modifying group memberships. The query searches for instances where the dseditgroup command includes the parameters -o edit, -a, and -t admin, which together represent a user being added to the administrative group. Before an event is flagged, the query performs a check to ensure that the process command line does not contain any of the whitelisted MDM identifiers specified earlier. This ensures that only potentially unauthorized or unexpected executions are surfaced as suspicious activity. Events meeting these criteria are labeled “User Added To Admin Group Via dseditgroup.”

After each of these detection paths has been processed, the results are combined using a union operation. This final step consolidates both potential methods of local admin privilege elevation into a single output dataset. The resulting data provides a clear view of all relevant events where users were added to the admin group through either dscl or dseditgroup within the defined timeframe. Each record includes detailed contextual information such as the device name, timestamp, initiating account, process command line, and the parent process responsible for the execution. This unified result allows analysts to easily review both legitimate and suspicious administrative group modifications across the macOS environment.

### KQL

```kql
   //if you are using an MDM Solution whitelist in the following line
   let legitimAdmin = dynamic(["jamfmanager","_automoxserviceaccount"]); 
   //User Added To Admin Group Via Dscl
   let NewAdminDSCL = DeviceProcessEvents
   | where Timestamp >= ago(1d)
   | where FileName == "dscl"
   | where ProcessCommandLine has_all ("-append", "/Groups/admin", "GroupMembership")
   | where not(ProcessCommandLine has_any (legitimAdmin))
   | extend Activity = "User Added To Admin Group Via Dscl";
   //User Added To Admin Group Via DseditGroup
   let NewAdminDSEDIT = DeviceProcessEvents
   | where Timestamp >= ago(1d)
   | where FileName == "dseditgroup"
   | where ProcessCommandLine has_all ("-o edit", "-a", "-t", "admin")
   | where not(ProcessCommandLine has_any (legitimAdmin))
   | extend Activity = "User Added To Admin Group Via Dseditgroup";
   //Root Account Enable Via Dsenableroot
   NewAdminDSCL
   | union NewAdminDSEDIT
```

## How to Investigate?

1. review the admin group modification event  
   - identify whether dscl or dseditgroup was used  
   - capture the full command line to see which user was added  
   - confirm the exact timestamp of the change  

2. validate the executing account  
   - determine which user or process ran the command  
   - check if this account normally performs privilege changes  
   - verify whether it aligns with approved IT or MDM activity  

3. analyze process origin  
   - review the parent process that launched dscl or dseditgroup  
   - check if it originated from a script, terminal session, or automation tool  
   - assess whether the execution context appears interactive or automated  

4. correlate with user activity  
   - identify the user that was added to the admin group  
   - check their recent login history and device usage  
   - determine if their role justifies elevated privileges  

5. assess timing patterns  
   - review if multiple admin additions occurred close together  
   - check if this event aligns with onboarding or maintenance windows  
   - look for unusual hours or rapid successive changes  

6. scope for related changes  
   - search for additional admin group modifications on other devices  
   - check for root account enablement or privilege escalation attempts  
   - identify whether similar commands appear across the environment
