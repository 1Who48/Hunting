## WSH-0055 CoPhish technique that abuses Microsoft Copilot Studio

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0055 CoPhish technique that abuses Microsoft Copilot Studio"_ has been created, how to use it.

### Required Access

These hunting cases are linked through a published application that grants us permission to perform threat hunting via the API in our customers' security portals.

### Custom Changes

* No custom changes are made.

## Overview

This detection hunts for illicit OAuth consent related to the CoPhish technique that abuses Microsoft Copilot Studio. It correlates:

* an endpoint session hitting copilotstudio.microsoft.com (likely where the social-engineering flow is hosted),
with

* a near-immediately following “Consent to application.” event in Entra ID (Azure AD),
and (optionally)

* subsequent Microsoft Graph API activity by the newly-consented application.

The goal is to expose cases where a user visits a trusted Microsoft domain that fronts a malicious consent flow, then grants permissions that attackers abuse via Graph API calls. This mirrors the Datadog Security Labs CoPhish write-up and current coverage of the technique.

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **DeviceNetworkEvents** module.

### How to Detect?

CoPhish uses a legitimate Microsoft domain to deliver the consent prompt, which reduces user suspicion. The near-time correlation to “Consent to application.” is a strong behavioral signal of a successful lure. Subsequent Graph API use by the same APPID shows the attacker beginning to use the granted permissions.

### KQL

```kql
    DeviceNetworkEvents
    | where TimeGenerated <= ago(1d)
    | where ActionType == "ConnectionSuccess"
    | where RemoteUrl has "copilotstudio.microsoft.com"
    | extend AccountUPN = InitiatingProcessAccountName
    | project StudioTimestamp=Timestamp, AccountUPN, DeviceName, ActionType, RemoteUrl
    | join kind=inner (
        CloudAppEvents
        | where TimeGenerated <= ago(1d)
        | where RawEventData.Workload == "AzureActiveDirectory"
        | where ActionType == "Consent to application."
        | extend AccountUPN = tostring(RawEventData.UserId)
        | extend APPID = ObjectId
        | project ConsentTimestamp=Timestamp, AccountUPN, AccountObjectId, ActionType, ObjectName, APPID
    ) on AccountUPN
    | where ConsentTimestamp between (StudioTimestamp .. 2m)
    | project StudioTimestamp, ConsentTimestamp, AccountUPN, AccountObjectId, DeviceName, RemoteUrl, ObjectName, APPID
    // optional Graph API correlation
    | join kind=inner (
        GraphAPIAuditEvents
        | extend GA_AccountObjectId = AccountObjectId
        | project ApplicationId, GA_AccountObjectId, RequestMethod, GraphAPITimeStamp=Timestamp, ResponseStatusCode, Scopes, RequestUri, IpAddress
    ) on $left.AccountObjectId == $right.GA_AccountObjectId
    | where ApplicationId == APPID
    | project StudioTimestamp, ConsentTimestamp, GraphAPITimeStamp, AccountUPN, RemoteUrl, ObjectName, Scopes, RequestMethod
```

## How to Investigate?

1. review the copilot studio access event  
   - confirm the exact time the user accessed copilotstudio.microsoft.com  
   - identify which device and account initiated the session  
   - determine if this access aligns with normal user activity or role  

2. analyze the application consent action  
   - review the application name and app ID that received consent  
   - check whether the user normally approves enterprise applications  
   - determine if the consent was user-initiated or admin-granted  

3. validate timing correlation  
   - confirm the consent occurred within the two-minute window after studio access  
   - assess whether this looks like a guided workflow or suspicious chaining  
   - look for repeated patterns across other users  

4. review granted permissions  
   - analyze the scopes granted to the application  
   - identify high-risk permissions (mail, files, directory access, etc.)  
   - assess whether permissions exceed business requirements  

5. inspect Graph API activity  
   - review request methods (GET, POST, PATCH, DELETE)  
   - check accessed endpoints in the request URI  
   - evaluate whether actions performed align with granted scopes  

6. correlate user behavior  
   - review the user’s recent sign-in history  
   - check for risky sign-ins or unusual locations/devices  
   - determine if similar app consents occurred previously
