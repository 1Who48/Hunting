## Overview

In late October 2025, security researchers uncovered a critical remote code execution flaw, CVE-2025-59287, quietly lurking in Windows Server Update Services (WSUS). The issue lay in a dangerously insecure deserialization routine tied to the AuthorizationCookie parameter — a small mistake that opened the door for unauthenticated attackers to gain full control over vulnerable servers. Once weaponized, this bug became a favorite among threat actors seeking to pivot from internal update servers into wider corporate networks.

The attacks followed a familiar rhythm. Exploit activity typically began with external connections to WSUS ports 8530 or 8531, often originating from unfamiliar or foreign IP addresses. These connections were the first hint that something was amiss, as WSUS servers are rarely exposed to the public internet. Not long after, the SoftwareDistribution.log file — normally a mundane record of update operations — would begin showing irregular modification patterns, suggesting tampering or unexpected write activity. From there, the most revealing sign of compromise appeared: WSUS-related processes, such as w3wp.exe (the IIS worker) or wsusservice.exe, spawning command-line interpreters like cmd.exe, powershell.exe, or net.exe. These process chains were unnatural for a legitimate update server and often the attacker’s bridge from code execution to full system takeover.

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **DeviceProcessEvents** module.

### How to Detect?

First, it looks for network connections targeting WSUS ports from non-private IP ranges, catching those suspicious inbound attempts that should never appear on a properly segmented server. Next, it watches for modifications to WSUS log files, a subtle forensic breadcrumb indicating that something inside the update process has changed. Finally, it tracks process creation events, specifically instances where the normally quiet WSUS services suddenly begin spawning potentially dangerous child processes associated with system reconnaissance or script execution.

Once all three elements align — an external hit to the WSUS port, a modified log file, and a suspicious process chain — the query correlates them into a single, high-severity signal. Each detection paints a timeline of compromise, showing when the attacker connected, what evidence was left behind, and how they attempted to escalate from a web request to system-level control.

### KQL

```kql
     let Lookback = 1d;  // Extended for post-disclosure hunting
     let WSUSPorts = dynamic([8530, 8531]);
     let SuspiciousProcesses = dynamic(["cmd.exe", "powershell.exe", "pwsh.exe", "whoami.exe", "net.exe", "net1.exe"]);
     // 1. Network connections to WSUS ports from external sources
     let WSUSNetworkActivity = 
     DeviceNetworkEvents
     | where Timestamp > ago(Lookback)
     | where LocalPort in (WSUSPorts)
     | where RemoteIP !startswith "127." and RemoteIP !startswith "10." and RemoteIP !startswith "192.168." and RemoteIP !startswith "172."
     | project DeviceId, Timestamp, RemoteIP, LocalPort, RemotePort;
     // 2. WSUS log file modifications (forensic artifacts)
     let WSUSLogModifications =
     DeviceFileEvents
     | where Timestamp > ago(Lookback)
     | where ActionType == "FileModified" or ActionType == "FileCreated"
     | where FileName == "SoftwareDistribution.log" 
     | where FolderPath has @"\\Program Files\\Update Services\\LogFiles\\" 
     | project DeviceId, Timestamp, FileName, FolderPath;
     // 3. WSUS processes spawning suspicious children
     let SuspiciousProcessChains =
     DeviceProcessEvents
     | where Timestamp > ago(Lookback)
     | join kind=inner (
     DeviceProcessEvents
     | where Timestamp > ago(Lookback)
     | where FileName in~ ("w3wp.exe", "wsusservice.exe")  // Parent WSUS/IIS processes
     | project ChildDeviceId=DeviceId, ChildTimestamp=Timestamp, ParentFileName=FileName, ParentProcessId=ProcessId
     ) on $left.InitiatingProcessId == $right.ParentProcessId
     | where FileName in~ (SuspiciousProcesses)  // Child processes of interest
     | where ProcessCommandLine has_any ("powershell -encodedCommand", "powershell -ec", "-EncodedCommand", "-ec", "whoami", "net user", "net group") 
     or FileName in~ ("whoami.exe", "net.exe", "net1.exe")  // indicators - Modify in case of Noice
     | project DeviceId, Timestamp, FileName, ProcessCommandLine, InitiatingProcessFileName, InitiatingProcessCommandLine, ParentFileName, FolderPath;
     // correlation
     let CompromisedDevices =
     WSUSNetworkActivity
     | summarize NetworkActivity = make_list(pack("Timestamp", Timestamp, "RemoteIP", RemoteIP, "LocalPort", LocalPort)) by DeviceId
     | join kind=inner (
     WSUSLogModifications
     | summarize LogActivity = make_list(pack("Timestamp", Timestamp, "FileName", FileName)) by DeviceId
     ) on DeviceId
     | join kind=inner (
     SuspiciousProcessChains
     | summarize ProcessActivity = make_list(pack("Timestamp", Timestamp, "FileName", FileName, "ProcessCommandLine", ProcessCommandLine, "ParentFileName", ParentFileName)) by DeviceId
     ) on DeviceId;
     // output with timeline
     SuspiciousProcessChains
     | join kind=inner (WSUSNetworkActivity) on DeviceId
     | join kind=inner (WSUSLogModifications) on DeviceId
     | join kind=inner (CompromisedDevices) on DeviceId
     | project Timestamp, DeviceId, ParentFileName, FileName, ProcessCommandLine, InitiatingProcessFileName, InitiatingProcessCommandLine, FolderPath, RemoteIP, LocalPort, LogFileModified = FileName1,  NetworkTimestamp = Timestamp1
     | order by Timestamp desc
     | extend Severity = "High"
```

## How to Investigate?

1. validate the exposed WSUS surface
   - confirm which devices accepted connections on 8530/8531 and verify they are actually WSUS/IIS hosts
   - review the remote ip addresses to determine if they are known partners, scanners, or truly unexpected sources
   - compare connection timing to business hours and typical wsus client communication patterns

2. analyze the suspicious process chain from wsus parents
   - confirm whether w3wp.exe or wsusservice.exe spawned the child processes (cmd, powershell, pwsh, whoami, net)
   - review the child process command lines for encoded powershell usage, discovery commands, and account/group enumeration
   - assess whether the initiating process command line indicates web request–driven execution or service-driven spawning

3. review wsus log file activity as a forensic signal
   - validate when SoftwareDistribution.log was created or modified relative to the network and process events
   - check if log modifications cluster tightly around the suspected exploitation window
   - identify whether modifications are abnormal compared to baseline log write behavior on that server

4. correlate event timeline for exploitation likelihood
   - build a time-ordered sequence across the three signals: external connection → process spawn → log modification
   - check for repeated sequences from the same remote ip or across multiple ports
   - identify whether multiple suspicious commands executed within a short window (suggesting interactive control)

5. evaluate command intent and next-stage objectives
   - categorize commands as execution (encoded powershell), discovery (whoami), and account manipulation/enumeration (net user/group)
   - look for indicators that commands were used to validate privileges, enumerate admins, or prepare lateral movement
   - review whether commands reference external urls, downloads, or payload staging locations

6. scope the pattern across devices and remote sources
   - check whether multiple device ids show the same combination of wsus port exposure, log modifications, and suspicious child processes
   - identify shared remote ips targeting several devices (campaign behavior) versus a single device (targeted)
   - compare parent/child process patterns across impacted servers to spot common exploitation tooling or tradecraft
