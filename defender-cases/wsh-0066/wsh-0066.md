## WSH-0066 EtherRAT Blockchain C2 Resolution via Public Ethereum RPC Endpoints

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0066 EtherRAT Blockchain C2 Resolution via Public Ethereum RPC Endpoints"_ has been created, how to use it.

### Required Access

These hunting cases are linked through a published application that grants us permission to perform threat hunting via the API in our customers' security portals.

### Custom Changes

* No custom changes are made.

## Overview

EtherRAT is a multi-stage remote access trojan built on Node.js, documented by Atos Threat Research Center (IoCs published at github.com/Atos-TRC/EtherRAT-appendixes). Initial access is achieved through trojanized MSI installers distributed via fake GitHub repositories that masquerade as popular system administration tools (PsExec, Sysmon, ProcDump, ScreenConnect, NSSM and roughly forty others), making IT staff and administrators the likely victims. The MSI uses a CustomAction to invoke a `.cmd` orchestrator that downloads a legitimate Node.js runtime from nodejs.org, stages AES-256-CBC encrypted JavaScript payloads under randomly named directories in the user's profile, and executes three obfuscated stages. Tasks received from the C2 are executed in-memory via the JavaScript `AsyncFunction` constructor, giving the operator arbitrary code execution, discovery, and screen capture capability.

The defining characteristic of the malware — and the basis of this detection — is its C2 resolution mechanism. Instead of hardcoding a C2 address, EtherRAT stores its current C2 URL in the state of an Ethereum smart contract. The implant issues `eth_call` requests (function selector `0x7d434425`) against nine hardcoded, legitimate public Ethereum RPC endpoints and cycles through them for redundancy. This lets the operator repoint the entire botnet to new infrastructure with a single blockchain transaction, without recompiling or redistributing the malware, and makes conventional domain/IP blocking of the C2 short-lived. The RPC endpoints themselves are legitimate public services, so this detection deliberately targets the *behaviour* — a non-browser process cycling through multiple public Ethereum RPC providers — rather than the endpoints as indicators. This behavioural approach also catches new EtherRAT builds whose C2 domains are not yet in any IoC feed.

### Attack Chain

| Stage | Binary / Method | Purpose |
|---|---|---|
| Initial Access | Fake GitHub repos / trojanized MSI | Victim manually downloads and runs an MSI posing as a well-known admin tool |
| Execution | `msiexec.exe` CustomAction (Type 1250) | Invokes `cmd.exe /c call <random>.cmd` at install sequence 4001 |
| Staging | `.cmd` orchestrator, `bitsadmin`, `tar` | Downloads Node.js v18.17.0/v20.10.0 from nodejs.org; commands split across variables to evade keyword detection; re-spawns hidden via `start /min` |
| Defense Evasion | Renamed Node.js binary, AES-256-CBC stages | Node.js renamed to a random string; encrypted payloads carry benign extensions (`.xml`, `.bak`, `.cfg`, `.dat`, `.bin`, `.ini`, `.tmp`); log file named `svchost.log` |
| C2 Resolution | `eth_call` (selector `0x7d434425`) to nine public Ethereum RPC endpoints | Reads the current C2 URL from attacker-controlled smart contract state; endpoint list hardcoded for failover |
| Command and Control | HTTPS POST, 60-second polling via `setInterval` | Tasks fetched from the resolved C2 URL and executed in-memory via `AsyncFunction`; payload can be re-obfuscated and re-executed in place |

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **DeviceNetworkEvents** module.

### How to Detect?

This rule detects the blockchain-based C2 resolution stage of EtherRAT. It searches `DeviceNetworkEvents` for connections to the nine public Ethereum RPC endpoints hardcoded in the malware, excludes common browsers (which generate legitimate traffic to these services through wallet extensions and dApps), and aggregates the remaining traffic per device and initiating process. Two signals drive triage: **endpoint cycling** — a single process contacting multiple distinct RPC providers is the malware's built-in failover behaviour, whereas legitimate applications typically use one configured provider — and **renamed Node.js** — a process whose PE original filename is `node.exe` but whose on-disk name differs, matching the documented masquerading TTP. Results are sorted so renamed-Node hits and high endpoint counts surface first. Note that this is a **low-fidelity** detection by design: legitimate cryptocurrency tooling, developer activity and blockchain-integrated software will also appear. The execution path of the initiating process is the primary triage pivot — legitimate Node.js runs from `Program Files\nodejs` or a version-manager path, not from randomly named directories under `AppData\Local`. Because the detection targets behaviour rather than C2 domains, it also catches new EtherRAT builds whose infrastructure is not yet published in IoC feeds.

### KQL

```kql
   let Lookback = 1d;
   let EthRpcHosts = dynamic([
       "eth.llamarpc.com", "mainnet.gateway.tenderly.co", "rpc.flashbots.net",
       "rpc.mevblocker.io", "eth-mainnet.public.blastapi.io", "ethereum-rpc.publicnode.com",
       "rpc.payload.de", "eth.drpc.org", "eth.merkle.io"
   ]);
   let Browsers = dynamic(["msedge.exe", "chrome.exe", "firefox.exe", "brave.exe", "opera.exe", "msedgewebview2.exe", "vivaldi.exe"]);
   DeviceNetworkEvents
   | where Timestamp > ago(Lookback)
   | where RemoteUrl has_any (EthRpcHosts)
   | where InitiatingProcessFileName !in~ (Browsers)
   // EtherRAT runs as a Node.js binary renamed to a random extensionless string:
   | extend RenamedNode = iff(InitiatingProcessVersionInfoOriginalFileName =~ "node.exe"
                              and InitiatingProcessFileName !~ "node.exe", true, false)
   | summarize Connections = count(), FirstSeen = min(Timestamp), LastSeen = max(Timestamp),
               RpcEndpoints = make_set(RemoteUrl), AnyRenamedNode = max(RenamedNode)
             by DeviceName, InitiatingProcessAccountName, InitiatingProcessFileName,
                InitiatingProcessFolderPath, InitiatingProcessVersionInfoOriginalFileName
   // A single non-browser process cycling through MULTIPLE public RPC endpoints
   // (the malware has all nine hardcoded) is the strongest signal:
   | extend RpcEndpointCount = array_length(RpcEndpoints)
   | sort by AnyRenamedNode desc, RpcEndpointCount desc, Connections desc
```

## How to Investigate?

1. **Assess the initiating process and its path**
   - The execution path is the primary triage pivot: legitimate Node.js runs from `C:\Program Files\nodejs\` or a version-manager path (`nvm`, `Volta`, `scoop`); EtherRAT stages under randomly named nested directories in the user profile, e.g. `AppData\Local\<random>\<random>\node.exe`
   - Check `AnyRenamedNode`: a process with PE original filename `node.exe` but a different on-disk name matches the documented masquerading TTP and is high confidence on its own
   - Note that `RpcEndpoints` may list the same host with and without an `https://` prefix; deduplicate before counting distinct providers

2. **Evaluate the endpoint-cycling behaviour**
   - A single process contacting several of the nine RPC providers indicates the malware's hardcoded failover list; legitimate applications typically use one configured provider
   - Sustained periodic connections over days or weeks indicate the implant's recurring C2-URL re-resolution rather than interactive developer or wallet activity

3. **Correlate with EtherRAT C2 infrastructure**
   - Pivot on the device and initiating process in `DeviceNetworkEvents` for connections to known EtherRAT C2 domains and IPs from the Atos TRC IoC list (github.com/Atos-TRC/EtherRAT-appendixes, `IoCs/domains.csv`) — a hit identifies the currently resolved, active C2 endpoint
   - Look for HTTPS POST traffic from the same process at a roughly 60-second polling cadence

4. **Locate staging and masquerading artefacts**
   - Inspect the process folder and its parents for encrypted payload stages carrying benign extensions (`.xml`, `.bak`, `.cfg`, `.dat`, `.bin`, `.ini`, `.tmp`)
   - Search `DeviceFileEvents` for `svchost.log` written outside `C:\Windows` — the malware's hardcoded log filename
   - Look for Node.js runtime downloads from nodejs.org via `bitsadmin`, `certutil`, `curl` or script hosts around the first-seen timestamp

5. **Establish initial access**
   - Review `DeviceProcessEvents` for the `msiexec.exe` → `cmd.exe /c call <random>.cmd` CustomAction chain preceding the first RPC connection
   - Check `DeviceFileEvents` (`FileOriginUrl`, `FileOriginReferrerUrl`) and browser history for downloads from the fake GitHub admin-tool repositories (`IoCs/malicious_github_repos.csv`); determine which tool the user intended to download
   - Identify the delivering MSI and preserve it for analysis

6. **Determine scope across the tenant**
   - Re-run this query and the C2 domain IoC hunt across all devices; the initial access vector (trojanized admin tools) plausibly affected multiple users, particularly IT staff
   - Given the malware targets administrators, review whether affected accounts hold privileged roles and whether those privileges were exercised during the dwell time

## How to Respond?

If the incident is identified as a true positive, proceed with standard remediation actions.

### Custom Remediation Actions

* Immediately isolate the affected device from the network; the implant polls for tasks every 60 seconds and supports arbitrary in-memory code execution
* Forensically preserve the full staging directory tree (including the renamed Node.js binary and encrypted payload stages), any `svchost.log` outside `C:\Windows`, the delivering MSI and `.cmd` orchestrator before remediation
* Reset credentials and revoke active sessions and refresh tokens for the affected user; review sign-in and audit activity across the full dwell time
* Assume data exposure for the entire infection window: EtherRAT performs discovery, screen capture and operator-tasked execution, so treat everything visible from the device and account as potentially compromised
* If the affected user holds administrative privileges, extend the investigation to systems and identities reachable with those privileges
* Hunt the estate for the remaining EtherRAT IoCs (C2 domains/IPs, fake GitHub repositories) and for the behavioural TTPs (MSI CustomAction chain, renamed Node.js execution, nodejs.org runtime downloads)
* Block or restrict the fake GitHub repository accounts at the web proxy, and consider warning IT staff about the trojanized admin-tool distribution vector
* Do not rely on blocking the resolved C2 domain alone — the operator can repoint the botnet via a single blockchain transaction; removal of the implant is the only durable remediation
