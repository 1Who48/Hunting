## WSH-0061 TeamPCP Trivy Supply Chain Compromise

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0061 TeamPCP Trivy Supply Chain Compromise"_ has been created, how to use it.

### Required Access

These hunting cases are linked through a published application that grants us permission to perform threat hunting via the API in our customers' security portals.

### Custom Changes

* No custom changes are made.

## Overview

TeamPCP is a threat campaign that targeted the open-source Trivy vulnerability scanner by injecting a malicious payload into its supply chain. When a compromised version of Trivy is executed — for example, within a CI/CD pipeline or developer workstation — it silently drops a credential harvester binary named `pglog` into `/tmp` to blend in with PostgreSQL tooling. The harvester bundles stolen credentials into a purpose-built archive (`tpcp.tar.gz`) and exfiltrates it over HTTP using a custom `X-Filename` header to attacker-controlled infrastructure, including several typosquatted domains mimicking legitimate security vendors such as Aqua Security and Checkmarx. To maintain persistence across restarts of the vulnerable `litellm` process, TeamPCP drops a masqueraded `systemd` unit (`sysmon.service`) and an associated Python script (`sysmon.py`) into the user's config directory — a strong anomaly given that Sysmon is a Windows-native tool with no legitimate Linux equivalent. The campaign was publicly disclosed by Microsoft on March 24, 2026.

### MITRE ATT&CK

This attack tactic can be mapped on the MITRE ATT&CK framework:

| MITRE Tactic          | Technique ID | Technique Name                                          | Relevance to Detection |
|-----------------------|--------------|---------------------------------------------------------|------------------------|
| Persistence           | T1543.002    | Create or Modify System Process: Systemd Service        | TeamPCP drops a masqueraded `sysmon.service` unit into `~/.config/systemd/user/` to survive process restarts and re-establish C2 |
| Defense Evasion       | T1036.005    | Masquerading: Match Legitimate Name or Location         | The credential harvester is named `pglog` and placed in `/tmp/pglog` to impersonate a PostgreSQL logging utility |
| Collection            | T1560.001    | Archive Collected Data: Archive via Utility             | Stolen credentials are bundled into `tpcp.tar.gz` prior to exfiltration |
| Exfiltration          | T1041        | Exfiltration Over C2 Channel                           | Credential archive is exfiltrated over HTTP with a custom `X-Filename: tpcp.tar.gz` header |
| Exfiltration          | T1567        | Exfiltration Over Web Service                           | Exfiltration targets include Cloudflare Tunnel endpoints and ICP-hosted infrastructure |
| Command and Control   | T1071.001    | Application Layer Protocol: Web Protocols               | C2 communication occurs over HTTP/S to typosquatted domains mimicking Aqua Security and Checkmarx |

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **DeviceProcessEvents**, **DeviceFileEvents**, **DeviceNetworkEvents**, **DeviceEvents**, and **CloudProcessEvents** modules.

### How to Detect?

This rule detects post-compromise activity associated with the TeamPCP Trivy supply chain campaign across eight detection branches, unified into a single daily hunt. Detection logic covers: outbound HTTP connections carrying the `X-Filename: tpcp.tar.gz` exfiltration header; network connections and DNS resolutions directed at known TeamPCP typosquatted C2 domains; creation of masqueraded `systemd` persistence files (`sysmon.service`, `sysmon.py`) in Linux user config directories; execution of the `pglog` credential harvester binary from `/tmp`; and creation, modification, or command-line references to the `tpcp.tar.gz` staging archive across both device and cloud process telemetry.

### KQL

```kql
   let lookback     = 1d;
   let archive_name = "tpcp.tar.gz";
   let c2_domains   = dynamic(["scan.aquasecurtiy.org", "aquasecurtiy.org", "checkmarx.zone", "plug-tab-protective-relay.trycloudflare.com", "tdtqy-oyaaa-aaaae-af2dq-cai.raw.icp0.io", "models.litellm.cloud"]);
   union isfuzzy=true
   (
   DeviceNetworkEvents
   | where Timestamp > ago(lookback)
   | where ActionType == "HttpConnection"
   | where AdditionalFields has "X-Filename: tpcp.tar.gz"
   | project Timestamp, DeviceId, DeviceName, DetectionName = "TeamPCP_ExfilHeader", Tactic = "Exfiltration", Technique = "T1041/T1567", ActionType, RemoteIP, RemoteUrl, RemotePort, FileName = InitiatingProcessFileName, FolderPath = "", ProcessCommandLine = InitiatingProcessCommandLine, AccountName = InitiatingProcessAccountName, AdditionalFields
   ),
   (
   DeviceNetworkEvents
   | where Timestamp > ago(lookback)
   | where RemoteUrl has_any (c2_domains)
   | project Timestamp, DeviceId, DeviceName, DetectionName = "TeamPCP_C2Domain_NetConn", Tactic = "Command and Control", Technique = "T1071.001/T1567", ActionType, RemoteIP, RemoteUrl, RemotePort, FileName = InitiatingProcessFileName, FolderPath = "", ProcessCommandLine = InitiatingProcessCommandLine, AccountName = InitiatingProcessAccountName, AdditionalFields = ""

   DeviceEvents

   | project Timestamp, DeviceId, DeviceName, DetectionName = "TeamPCP_C2Domain_DNS", Tactic = "Command and Control", Technique = "T1071.001", ActionType, RemoteIP = "", RemoteUrl = coalesce(DnsQueryString, tostring(AdditionalFields)), RemotePort = int(0), FileName = InitiatingProcessFileName, FolderPath = "", ProcessCommandLine = InitiatingProcessCommandLine, AccountName = InitiatingProcessAccountName, AdditionalFields

   | where Timestamp > ago(lookback)

   (
   DeviceProcessEvents
   | where Timestamp > ago(lookback)
   | where FolderPath =~ "/tmp/pglog" or (FolderPath startswith "/tmp/" and FileName =~ "pglog")

   ),
   (
   DeviceProcessEvents
   | where Timestamp > ago(lookback)
   | where ProcessCommandLine has archive_name
   | project Timestamp, DeviceId, DeviceName, DetectionName = "TeamPCP_ArchiveStaging_Process", Tactic = "Collection", Technique = "T1560.001", ActionType, RemoteIP = "", RemoteUrl = "", RemotePort = int(0), FileName, FolderPath, ProcessCommandLine, AccountName, AdditionalFields = ""
   ),
   (
   CloudProcessEvents
   | where Timestamp > ago(lookback)
   | where ProcessCommandLine has archive_name
   | project Timestamp, DeviceId = "", DeviceName = "", DetectionName = "TeamPCP_ArchiveStaging_CloudProc", Tactic = "Collection", Technique = "T1560.001", ActionType = "ProcessCreated", RemoteIP = "", RemoteUrl = "", RemotePort = int(0), FileName, FolderPath = "", ProcessCommandLine, AccountName, AdditionalFields = ""
   ),
   (
   DeviceFileEvents
   | where Timestamp > ago(lookback)
   | where ActionType in ("FileCreated", "FileModified", "FileRenamed")
```

## How to Investigate?

1. **Identify the detection branch that fired**
   - Review `DetectionName` to understand which specific indicator triggered the alert
   - Use `Tactic` and `Technique` to frame the stage of the attack lifecycle the activity represents
   - Correlate the `Timestamp` and `DeviceName` to establish when and where the activity occurred

2. **Investigate process execution context**
   - For `TeamPCP_pglogMasquerade` and archive staging detections, review `FileName`, `FolderPath`, and `ProcessCommandLine` for execution from anomalous paths such as `/tmp`
   - Check `AccountName` to determine whether the activity ran under a service account, CI/CD runner identity, or interactive user session
   - Trace parent process context to determine whether Trivy or a related CI/CD tool was the originating process

3. **Analyse file activity**
   - For `TeamPCP_SystemdPersistence`, confirm whether both `sysmon.py` and `sysmon.service` were created on the same device within a short timeframe, indicating a complete persistence installation
   - For `TeamPCP_ArchiveStaging_File`, check `FolderPath` to determine where the archive was staged and whether it was subsequently accessed or exfiltrated
   - Correlate file creation timestamps with process and network events to reconstruct the activity chain

4. **Review network and DNS communication**
   - For `TeamPCP_ExfilHeader`, review `RemoteIP`, `RemoteUrl`, and `RemotePort` to confirm the exfiltration destination and whether the connection completed successfully
   - For `TeamPCP_C2Domain_NetConn` and `TeamPCP_C2Domain_DNS`, determine whether a full TCP session was established or whether the connection was blocked at the DNS or network layer
   - Check whether multiple C2 domains were contacted from the same device, which may indicate active operator interaction or automated fallback logic

5. **Assess scope and lateral spread**
   - Determine whether the same `AccountName` or CI/CD runner identity was used across multiple devices or pipeline runs
   - Check whether the compromised Trivy version was executed in multiple environments (e.g., development, staging, production)
   - Identify any downstream systems that may have been exposed to credentials harvested by `pglog`

6. **Reconstruct the full attack timeline**
   - Build a chronological view of all eight detection branches across the affected device
   - Look for the sequence: Trivy execution → pglog drop → tpcp.tar.gz creation → HTTP exfiltration → sysmon persistence
   - Identify whether any C2 callbacks occurred after the initial exfiltration, indicating continued attacker access via the systemd persistence mechanism

## How to Respond?

If the incident is identified as a true positive, proceed with standard remediation actions.

### Custom Remediation Actions

* Revoke and rotate any credentials that may have been accessible to the compromised Trivy process, including cloud provider keys, container registry tokens, and CI/CD secrets
* Audit pipeline configurations to identify all jobs that executed the compromised Trivy version and treat their secret scopes as fully compromised
* Remove the `sysmon.service` systemd unit and `sysmon.py` script from affected devices and reload the systemd daemon to prevent re-execution
* Terminate and remove the `pglog` binary from `/tmp/pglog` and scan for any additional files dropped in `/tmp` during the same timeframe
* Block the known TeamPCP C2 domains and IPs at the perimeter firewall and DNS filtering layer
