## WSH-0017 RDP enable by modifying registry key

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0017 RDP enable by modifying registry key"_ has been created, how to use it.

### Required Access

These hunting cases are linked through a published application that grants us permission to perform threat hunting via the API in our customers' security portals.

### Custom Changes

* No custom changes are made.

## Overview

Attackers can attempt to enable RDP, including leveraging multiple living-off-the-land tools. Once RDP is enabled, it allows the attackers to use any number of dual-use tools that leverage the RDP protocol. The following query will hunt for an attempt to enable RDP by simply modifying a registry key.

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **Device Protect** module.

### How to Detect?

The **"DeviceProcessEvents"** we can hunt on modification on the Reg file that enable RDP.


### KQL

```kql
    let rdpcommands = dynamic([@"fDenyTSConnections", @"REG_DWORD /d 0"]);
    DeviceProcessEvents
    | where Timestamp > ago(1d)
    | where FileName has @"reg.exe"
    | where ProcessCommandLine has_all (rdpcommands)
    | project DeviceId, DeviceName, ProcessCommandLine, Start = Timestamp
    | join kind = inner (DeviceRegistryEvents
    | where RegistryKey == @"HKEY_LOCAL_MACHINE\SYSTEM\ControlSet001\Control\Terminal Server"
    | where RegistryValueName == @"fDenyTSConnections"
    | where ActionType == @"RegistryValueSet"
    | where RegistryValueData == @"0"
    | where InitiatingProcessFileName == @"reg.exe"
    | project DeviceId, End = Timestamp)
    on DeviceId
    | where (End - Start) between (0min .. 1min)
    | project Start, DeviceId, DeviceName, ProcessCommandLine
```

## How to Investigate?

1. Confirm authorization and change intent
    * Verify whether enabling RDP on the affected device was approved, documented, or part of legitimate remote support activity.
    * Identify the user or service account that executed the registry change and validate their administrative role.

2. Assess the access exposure
    * Enabling fDenyTSConnections = 0 allows inbound RDP—determine whether the device was previously restricted and why the change was made.
    * Check whether network controls, firewall rules, or security baselines were also modified to support RDP access.

3. Analyze execution context
    * Review how reg.exe was launched (interactive admin shell, script, scheduled task, or malware execution).
    * Look for suspicious parent processes or execution shortly after other attacker behaviors.

4. Correlate with RDP authentication activity
    * Investigate whether RDP logons occurred soon after the registry change, especially from unfamiliar IPs or geographies.
    * Watch for brute-force attempts, new local admin usage, or abnormal session durations.

5. Check for persistence and lateral movement
    * Determine whether additional registry keys, services, or firewall rules were modified to maintain long-term access.
    * Look for signs the host was used as a pivot point to access other systems.
