## WSH-0063 BlueHammer VSS Shadow Copy and Registry Hive Credential Access

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0063 BlueHammer VSS Shadow Copy and Registry Hive Credential Access"_ has been created, how to use it.

### Required Access

These hunting cases are linked through a published application that grants us permission to perform threat hunting via the API in our customers' security portals.

### Custom Changes

* No custom changes are made.

## Overview

BlueHammer is a credential harvesting technique that combines Volume Shadow Copy Service (VSS) abuse with direct registry hive access to extract password hashes and LSA secrets from managed endpoints without touching LSASS memory — the most commonly monitored credential dumping vector. The attack chain begins with the creation of a VSS shadow copy using native Windows binaries (`vssadmin.exe`, `wmic.exe`, `diskshadow.exe`) or PowerShell WMI calls targeting `Win32_ShadowCopy`. Once the shadow volume is created, the threat actor accesses the registry hives (`HKLM\SAM`, `HKLM\SYSTEM`, `HKLM\SECURITY`) directly from the shadow copy, allowing the offline extraction of NTLM hashes, cached domain credentials, and LSA secrets without triggering LSASS-based detections such as process injection alerts or Credential Guard bypass warnings.

This approach is favored by ransomware operators and post-exploitation frameworks (including Impacket, CrackMapExec, and custom tooling) during the lateral movement phase, as the extracted hashes can be used directly in Pass-the-Hash attacks or cracked offline. Because VSS creation is a legitimate administrative operation and registry reads of `HKLM\SYSTEM` are common, individual events may not trigger alerts — this detection focuses on the correlated chain of both events occurring on the same device within a configurable time window.

### Attack Chain

| Stage | Binary / Method | Purpose |
|---|---|---|
| Shadow Copy Creation | `vssadmin.exe create shadow` | Creates a point-in-time snapshot of the volume containing the registry hives |
| Shadow Copy Creation | `wmic shadowcopy call create` | Alternative WMI-based method for VSS creation |
| Shadow Copy Creation | `diskshadow.exe` | Alternative VSS creation via interactive or script mode |
| Shadow Copy Creation | `powershell.exe` + `Win32_ShadowCopy` | PowerShell WMI invocation to create shadow copies programmatically |
| Registry Hive Access | `HKLM\SAM` | Contains local account NTLM password hashes |
| Registry Hive Access | `HKLM\SYSTEM` | Contains the SYSKEY used to decrypt SAM entries |
| Registry Hive Access | `HKLM\SECURITY` | Contains LSA secrets including cached domain credentials and service account passwords |

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **DeviceProcessEvents** and **DeviceRegistryEvents** modules.

### How to Detect?

This rule detects the BlueHammer attack chain by correlating VSS shadow copy creation events in `DeviceProcessEvents` with registry hive access events in `DeviceRegistryEvents` on the same device within a configurable time window (default: 1 day). Both events must occur on the same `DeviceId` and the hive access must follow the shadow copy creation within the defined window. The detection covers `vssadmin.exe`, `wmic.exe`, `diskshadow.exe`, and PowerShell-based VSS creation, and matches on `RegistryKeyRead`, `RegistryValueRead`, and `RegistryKeyOpened` actions targeting the SAM, SYSTEM, and SECURITY hives.

### KQL

```kql
   let TimeWindow = 1d; // Tunable: time window for chain correlation
   let VSSCreation = DeviceProcessEvents
      | where Timestamp > ago(1d)
      | where FileName in~ ("vssadmin.exe", "wmic.exe", "diskshadow.exe") or (FileName =~ "powershell.exe" and ProcessCommandLine has_any ("ShadowCopy", "Win32_ShadowCopy", "vssadmin", "create shadow"))
      | where ProcessCommandLine has_any ("create", "shadow", "shadowcopy")
      | project VSSTime = Timestamp, DeviceId, VSSInitiatingProcess = InitiatingProcessFileName,VSSInitiatingPid = InitiatingProcessId, AccountName, AccountDomain,VSSCommandLine = ProcessCommandLine;
   let HiveAccess = DeviceRegistryEvents
      | where Timestamp > ago(1d)
      | where RegistryKey has_any (@"HKLM\SAM",@"HKLM\SYSTEM",@"HKLM\SECURITY",@"MACHINE\SAM",@"MACHINE\SYSTEM",@"MACHINE\SECURITY")
      | where ActionType in ("RegistryValueRead", "RegistryKeyRead", "RegistryKeyOpened")
      | project HiveTime = Timestamp, DeviceId, HiveProcess = InitiatingProcessFileName, HivePid = InitiatingProcessId, RegistryKey, ActionType;
   VSSCreation
   | join kind=inner (HiveAccess) on DeviceId
   | where HiveTime between (VSSTime .. (VSSTime + TimeWindow))
   | project-reorder VSSTime, HiveTime, DeviceId, AccountName, AccountDomain, VSSInitiatingProcess, VSSCommandLine, HiveProcess, RegistryKey
   | sort by VSSTime desc
```

## How to Investigate?

1. **Identify the VSS creation method**
   - Review `VSSInitiatingProcess` and `VSSCommandLine` to determine which binary or method was used to create the shadow copy
   - Legitimate administrative use of `vssadmin.exe` or `wmic.exe` is possible; correlate with the account context and scheduled maintenance windows
   - PowerShell-based VSS creation (`Win32_ShadowCopy`) is less common in legitimate operations and warrants higher suspicion
   - Review `AccountName` and `AccountDomain` to determine whether the account has a legitimate reason to manage shadow copies

2. **Assess the registry hive access**
   - Review `HiveProcess` to identify which process accessed the registry hives
   - Access to `HKLM\SAM` combined with `HKLM\SYSTEM` is a strong indicator of credential extraction, as both are required to decrypt local password hashes
   - Determine whether the process performing the hive access is a known tool (e.g., `reg.exe`, `secretsdump.py`, custom tooling) or an unexpected process
   - Check the `HivePid` to correlate with other process events and identify the parent process tree

3. **Correlate the timing of both events**
   - Confirm that the registry hive access (`HiveTime`) occurred after the VSS creation (`VSSTime`) and within the `TimeWindow`
   - A short time delta (seconds to minutes) between VSS creation and hive access is a strong indicator of automated tooling
   - Review whether shadow copies were deleted shortly after creation, which is indicative of ransomware or post-exploitation cleanup

4. **Investigate the account context**
   - Determine whether `AccountName` is a local administrator, domain administrator, or service account
   - Check for signs of privilege escalation prior to the VSS creation event
   - Review logon events for the account to determine whether the session was initiated interactively, via remote desktop, or via a remote execution framework (PsExec, WMI, WinRM)

5. **Check for lateral movement indicators**
   - Search `DeviceLogonEvents` for unusual logon activity on the affected device in the hours preceding the detection, particularly network logons (`LogonType 3`) from unexpected source IPs
   - Review `DeviceNetworkEvents` for outbound connections to unknown or suspicious hosts occurring after the hive access, which may indicate credential exfiltration
   - Identify whether the same account or extracted credentials were subsequently used on other devices in the environment

6. **Assess scope across the environment**
   - Determine whether the same VSS + hive access chain has occurred on additional devices across the tenant
   - Identify whether multiple accounts' credentials may have been exposed
   - Check whether domain controller devices are affected, as NTDS.dit extraction via VSS is a separate but related technique that may follow this activity

## How to Respond?

If the incident is identified as a true positive, proceed with standard remediation actions.

### Custom Remediation Actions

* Immediately isolate the affected device from the network to prevent lateral movement using credentials that may have been extracted
* Force a password reset for all local accounts on the affected device, as NTLM hashes may have been extracted and are usable in Pass-the-Hash attacks without cracking
* Force a password reset for any domain accounts that were logged on to the affected device during or before the detection window, prioritising privileged accounts and service accounts
* Rotate LSA secrets and service account credentials on the affected device, including any accounts whose credentials are stored as cached domain verifiers
* Delete all VSS shadow copies on the affected device after forensic preservation to remove attacker-created snapshots that may still be accessible
* Review and restrict VSS creation privileges using group policy (`Manage auditing and security log` and `Back up files and directories`) to limit which accounts can create shadow copies
* Enable Windows Credential Guard on affected endpoints where applicable to prevent future offline credential extraction from registry hives
* Review post-exploitation tooling indicators — search for known credential dumping tool artifacts (e.g., `secretsdump`, Impacket output files, `mimikatz` variants) on the affected device
