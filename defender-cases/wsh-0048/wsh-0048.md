## WSH-0048 Azure activities from high-risk users

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

The purpose of this document is to explain why usecase _"WSH-0048 Azure activities from high-risk users"_ has been created and how to use it.

This usecase detects Azure activities from high-risk users.

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **Identity Protect Cloud** module.

### How to Detect?

The **"AuditLogs"** table can be used to hunt for action on user/guest accounts. Related activities will be detected with the following KQL query:

### KQL

```kql
    let riskyAzureSignIns = ( 
    AADSignInEventsBeta 
    | where Timestamp > ago(1d) 
    | where ErrorCode == 0 
    | where Application == "Azure Portal" 
    | where RiskLevelAggregated == 100 or RiskLevelDuringSignIn == 100 
    | project AccountObjectId, RiskySignInTimestamp = Timestamp); 
    let AzureActivity = (  
    CloudAppEvents 
    | where Timestamp > ago(30d) 
    | where Application == "Microsoft Azure" 
    | project AccountObjectId, ActivityTime = Timestamp); 
    //join the tables 
    riskyAzureSignIns 
    | join AzureActivity on AccountObjectId  
    | where ActivityTime between (RiskySignInTimestamp .. (RiskySignInTimestamp + 12h)) 
```

## How to Investigate?

1. validate the risky sign-in details
   - review why the sign-in was rated high risk (location anomaly, TOR, unfamiliar device, impossible travel)
   - check source IP, geo-location, device ID, and MFA status
   - confirm whether the user recognizes the login

2. analyze post-login Azure activity
   - identify what actions were performed within the 12-hour window
   - check for resource creation, role assignments, or security setting changes
   - look for unusual or high-impact operations

3. assess account privilege level
   - determine if the account has admin or contributor permissions
   - identify scope of access (subscription, tenant, management group)
   - evaluate potential impact of actions taken

4. correlate with other identity signals
   - review sign-in history for repeated risky logins
   - check for MFA failures or bypass patterns
   - identify concurrent logins from different locations

5. evaluate automation vs interactive behavior
   - determine if actions were performed via portal, API, or scripts
   - check user agents for suspicious tooling
   - review timing patterns for scripted behavior

6. scope across the environment
   - search for similar risky sign-ins on other accounts
   - identify shared IPs or devices
   - look for coordinated activity across multiple users
