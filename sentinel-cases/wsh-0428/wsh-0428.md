## WSH-0428 Azure Storage Mass File Deletion

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0428 Azure Storage Mass File Deletion"_ has been created, how to use it.

## Overview

Detect mass file deletion events within Azure File and Blob storage. deleteWindow controls the period of time the deletions must occur in, whilst the deleteThreshold controls how many files must be deleted within that threshold. Query works on a per-IP address basis, so will only detect a single IP deleting multiple files.

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **Azure Landingzone** module.

### How to Detect?

The **"StorageFileLogs"** and **"StorageBlobLogs"** logs of the customer need to be exported to the Wortell MDR Sentinel Log Analytics Workspace with the Microsoft Sentinel **"Azure Storage Account"** connector of Sentinel.

### KQL

```kql
   let deleteThreshold = 100;          // tune to your environment baseline
   let deleteWindow    = 10m;
   let lookback        = 1d;
   // Optional: exclude known automation principals / service IPs
   let ExcludedIdentities = _GetWatchlist('WSH-0428 Azure Storage Mass File Deletion');
   let ExcludedIPs        = dynamic([]);
   union isfuzzy=true StorageFileLogs, StorageBlobLogs
   | where TimeGenerated > ago(lookback)
   | where StatusText =~ "Success"
   | where OperationName in~ ("DeleteBlob", "DeleteFile", "DeleteDirectory")
   | extend CallerIpAddress = tostring(split(CallerIpAddress, ":", 0)[0])
   | extend Identity = coalesce(
            tostring(column_ifexists("RequesterObjectId", "")),
            tostring(column_ifexists("RequesterUpn", "")),
            tostring(column_ifexists("RequesterAppId", "")),
            AuthenticationType)
   | where Identity        !in (ExcludedIdentities)
   | where CallerIpAddress !in (ExcludedIPs)
   | summarize
            FilesDeleted = dcount(Uri),
            FirstDelete  = min(TimeGenerated),
            LastDelete   = max(TimeGenerated),
            SampleUris   = make_set(Uri, 5),
            Operations   = make_set(OperationName)
   by bin(TimeGenerated, deleteWindow),
   AccountName, Identity, AuthenticationType, CallerIpAddress, UserAgentHeader
   | where FilesDeleted >= deleteThreshold
   | extend DurationMin   = datetime_diff('minute', LastDelete, FirstDelete) + 1
   | extend DeletesPerMin = round(todouble(FilesDeleted) / DurationMin, 2)
   | project TimeGenerated, FirstDelete, LastDelete, AccountName, Identity,
            AuthenticationType, IPCustomEntity=CallerIpAddress,
            UserAgentHeader, FilesDeleted, DeletesPerMin, SampleUris, Operations
   | order by FilesDeleted desc
```

## How to Investigate?

1. Validate the deletion burst and threshold logic
   - Confirm the activity occurred within the last 24 hours and the deletes were marked Success
   - Review the 10-minute time bins and verify the FilesDeleted count meets or exceeds 3 unique URIs per window
   - Determine whether the deletions are isolated to a single spike or repeated across multiple windows

2. Profile the caller identity and access method
   - Review AccountName to determine whether the actor is a user, application identity, automation account, or service principal context represented in the logs
   - Examine CallerIpAddress for consistency and whether it matches known corporate egress, cloud infrastructure, or unexpected sources
   - Review UserAgentHeader to identify the tooling used (portal, SDK, CLI, AzCopy, custom script, unknown client)

3. Characterize what was deleted and where
   - Pivot from the summarized event to understand which URIs were deleted and whether they map to a specific container/share, directory, or workload
   - Determine whether deletions are concentrated in one storage area or spread across multiple paths
   - Assess whether the naming patterns suggest routine lifecycle cleanup versus targeted removal of specific content

4. Correlate with adjacent storage operations and session behavior
   - Review other storage actions around the same time from the same AccountName and CallerIpAddress (reads, listings, writes) to understand lead-up behavior
   - Check whether deletes followed bulk listing or download activity, which can indicate preparation steps
   - Determine whether activity cadence appears scripted (regular intervals) or interactive (bursty, irregular)

5. Assess scope across IPs, accounts, and user agents
   - Check whether multiple CallerIpAddress values are associated with deletions against the same AccountName, suggesting distributed automation or shared credentials
   - Determine whether the same CallerIpAddress is deleting across multiple AccountName values, suggesting a common tool or jump point
   - Compare UserAgentHeader strings across hits to identify shared tooling or a single anomalous client

6. Build an investigation narrative for each hit
   - Document the time window, AccountName, CallerIpAddress, UserAgentHeader, and FilesDeleted count as the core pivot points
   - Identify whether the pattern aligns with known operational jobs (backup rotation, retention cleanup) based on timing and tooling signals
   - Capture notable anomalies (unfamiliar IP, rare user agent, unusual storage path concentration) for deeper follow-up
