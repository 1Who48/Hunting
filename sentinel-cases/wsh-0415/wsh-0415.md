## WSH-0415 New Child Process of W3WP.exe

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _" WSH-0415 New Child Process of W3WP.exe"_ has been created, how to use it.

### Required MDR Modules and Sentinel Connectors

| MDR Module                 | Required Data Connectors          |
| -------------------------- | ----------------------------------|
| **Device Protect**         | Windows Security Events via AMA   |

### Custom Changes

* No customer changes are made for this hunt case.

## Overview

This Hunting Query looks for child processes of w3wp.exe that have not been seen as a child process on that host

### MITRE ATT&CK

This attack tactic can be mapped on the MITRE ATT&CK framework:

| Tactic                | Techniques |
|-----------------------|------------|
| Execution             | T1203      |

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **Device Protect** module.

### How to Detect?

The **"DeviceActivity"** logs of the customer need to be exported to the Wortell MDR Sentinel Log Analytics Workspace with the Microsoft Sentinel **"Windows Security Events via AMA"** connector of Sentinel.

### KQL

```kql
    let starttime = ago(3d);
    let endtime = now();
    let lookback = starttime - 14d;
    let known_procs = (
        SecurityEvent
        | where TimeGenerated between(lookback .. starttime)
        | where EventID == 4688
        | where ParentProcessName hassuffix "w3wp.exe"
        | extend ProcessHost = strcat(Process, "-", Computer)
        | summarize by ProcessHost);
    SecurityEvent
    | where TimeGenerated between(starttime .. endtime)
    | where EventID == 4688
    | where ParentProcessName hassuffix "w3wp.exe"
    | extend ProcessHost = strcat(Process, "-", Computer)
    | where ProcessHost !in (known_procs)
    | project-reorder TimeGenerated,Computer,NewProcessName,ParentProcessName,Account,NewProcessId
    | extend timestamp = TimeGenerated,HostCustomEntity = Computer,AccountCustomEntity = Account
```

## How to Investigate?

1. Validate what makes the process spawning unusual
   - Confirm the event is a process creation (4688) where the parent is w3wp.exe (IIS worker process)
   - Note the 3-day detection window and that the process+host combination did not appear in the prior 14-day baseline
   - Review whether the “new” condition is driven by a new process name, a new host, or both

2. Profile the affected server and IIS context
   - Identify the role of the Computer (web server, Exchange, app server) and whether IIS-hosted apps are expected to spawn child processes
   - Determine which site/application pool is likely associated with the w3wp.exe instance for that timeframe
   - Check for recent deployments or configuration changes that could explain new child process behavior without assuming benign intent

3. Analyze the spawned process details
   - Review NewProcessName for script engines, command interpreters, living-off-the-land binaries, or uncommon executables for an IIS worker to launch
   - Capture the NewProcessId and correlate it with additional telemetry to understand runtime behavior and lifetime
   - Determine whether the process path suggests system binary usage, app directory execution, temp directory execution, or unexpected locations

4. Examine the account context and execution chain
   - Review the Account to determine whether the process ran under an application pool identity, a service account, or another user context
   - Correlate with logon/session context to see whether the activity is tied to interactive admin access or purely server-side execution
   - Assess whether multiple distinct accounts are associated with similar w3wp.exe-spawned activity on the same host

5. Correlate with web activity preceding the spawn
   - Review IIS and application logs around the same timestamp to identify the inbound request path, method, and client source that preceded the child process creation
   - Look for unusual URL patterns, repeated requests, or error bursts that coincide with the first appearance of the new process
   - Determine whether the timing aligns with known application endpoints that legitimately invoke external processes

6. Scope and pattern-match across hosts and time
   - Check whether the same NewProcessName appears as a new w3wp.exe child on other servers, indicating broader propagation or a common app behavior change
   - Determine whether the events cluster tightly (burst) or occur periodically (scheduled or triggered behavior)
   - Document the first-seen time, affected hosts, process names, and accounts to build an investigation narrative
