## WSH-0432 Scheduled Task Creation or Update from User Writable Directory

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0432 Scheduled Task Creation or Update from User Writable Directory"_ has been created, how to use it.

### Required MDR Modules and Sentinel Connectors

| MDR Module                 | Required Data Connectors |
| -------------------------- | ------------------------ |
| **Device Protect**         | Microsoft Defender for Endpoint |
|                            | Azure Active Directory |
|                            | Microsoft 365 Defender |

## Overview

This query triggers when a scheduled task is created or updated and it is going to run programs from writable user paths.

### MITRE ATT&CK

This attack tactic can be mapped on the MITRE ATT&CK framework:

| Tactic                | Techniques |
|-----------------------|------------|
| Execution             | T1053      |

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **Device Protect** module.

### How to Detect?

The **"SecurityEvent"** logs of the customer need to be exported to the Wortell MDR Sentinel Log Analytics Workspace with the Microsoft Sentinel **"Microsoft Defender for Endpoint"** connector of Sentinel.

### KQL

```kql
    let WritableUserPaths = dynamic (["\"C:\\Users\\","\"C:\\ProgramData\\"]);
    SecurityEvent
    | where TimeGenerated > ago(1d)
    | where EventID in (4698,4702) and EventData has_any (WritableUserPaths)
    | parse EventData with * 'Command&gt;' Command "&lt" *
    | parse EventData with * 'Arguments&gt;' Arguments "&lt" *
    | where Command has_any (WritableUserPaths) or Arguments has_any (WritableUserPaths)
    | parse EventData with * 'SubjectUserName">' SubjectUserName "<" * 'SubjectDomainName">' SubjectDomainName "<" * 'TaskName">' TaskName "<" *
    | summarize StartTime = min(TimeGenerated), EndTime = max(TimeGenerated) by Activity, Computer, SubjectUserName, SubjectDomainName, TaskName, Command, Arguments
    | extend CommandLine = strcat(split(Command, '\\')[-1], ' ', Arguments)
    | extend HostName = tostring(split(Computer, '.', 0)[0]), DnsDomain = tostring(strcat_array(array_slice(split(Computer, '.'), 1, -1), '.'))
    | extend Account_0_Name = SubjectUserName
    | extend Account_0_NTDomain = SubjectDomainName
    | extend Host_0_HostName = HostName
    | extend Host_0_DnsDomain = DnsDomain
    | extend Process_0_CommandLine = CommandLine
```

## How to Investigate?

1. Validate the scheduled task change event and timing
   - Confirm whether the event represents task creation (4698) or task update (4702)
   - Review StartTime and EndTime to understand whether this was a one-off change or multiple modifications
   - Note the Computer and TaskName to ensure you are looking at the intended task and host

2. Review why the task is considered suspicious
   - Confirm that the task Command or Arguments reference writable user paths (C:\Users\ or C:\ProgramData\)
   - Identify the exact executable/script path and whether it resides in a user-writable directory rather than a standard program location
   - Review the constructed CommandLine (executable name plus arguments) for unusual switches, hidden execution, or chained commands

3. Assess the task identity and ownership context
   - Review SubjectUserName and SubjectDomainName to determine who created or modified the task
   - Determine whether that account typically administers scheduled tasks on the affected host
   - Correlate with recent logon activity for the same account to understand whether the change was interactive, remote, or automated

4. Examine the task semantics and execution behavior
   - Review the task’s purpose by inspecting its name, referenced paths, and arguments for clues (update mechanism vs launcher behavior)
   - Determine whether the task likely runs on a trigger (logon/startup/schedule) versus on-demand execution patterns
   - Check whether the task configuration suggests persistence-like behavior (repeated runs, short intervals, execution on logon)

5. Correlate with file and process activity around the task change
   - Review whether the referenced executable/script was created or modified shortly before the task was created/updated
   - Check for process execution events matching the task’s command line after the change window
   - Identify whether the task action points to recently dropped files in the same writable directory

6. Scope similar task patterns across the environment
   - Determine whether similar TaskName patterns, command paths, or writable-directory task actions appear on other hosts
   - Check whether the same SubjectUserName is associated with scheduled task changes on multiple systems
   - Document per hit: host, task name, creator/updater, writable path used, and the intended command line
