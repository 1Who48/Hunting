## WSH-0412 Network Connection to New External LDAP Server

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0412 Network Connection to New External LDAP Server"_ has been created, how to use it.

### Required MDR Modules and Sentinel Connectors

| MDR Module                       | Required Data Connectors            |
|--------------------------------- |------------------------------------ |
| **Identity Protect On-Premises** | Security Events via Legacy Agent or |
|                                  | Windows Security Events via AMA or  |
|                                  | Windows Forwarded Events (Preview)  |

## Overview

This hunting query looks for outbound network connections using the LDAP protocol to external IP addresses, where that IP address has not had an LDAP network connection to it in the 7 days preceding the query timeframe

### MITRE ATT&CK

This attack tactic can be mapped on the MITRE ATT&CK framework:

| Tactic                | Techniques |
|-----------------------|------------|
| Exfiltration          | T1190      |

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **Identity Protect On-Premises** module.

### How to Detect?

For every in scope server (_see the table below_) the **"SecurityEvents"** need to be uploaded to the Wortell MDR Sentinel Log Analytics Workspace with the Microsoft Sentinel  **"Security Events"** connector (or the **"Windows Security Events via AMA"** connector or the **"Windows Forwarded Events"** connector depending on the situation).

| MMA/AMA Installation on:                     |
| -------------------------------------------- |
| Domain Controllers (AD DS)                   |
| Active Directory Federation Services (AD FS) |
| DNS (DNS)                                    |
| AAD Connect                                  |
| AD Certificate Services (AD CS)              |

### KQL

```kql
    let starttime = 1d;
    let endtime = 1h;
    let legacy_ldap = (
    CommonSecurityLog
    | where TimeGenerated between (ago(starttime) .. ago(endtime))
    // Filter to LDAP connections only
    | where ApplicationProtocol =~ "ldap"
    // Check LDAP server is external
    | extend private =  ipv4_is_private(DestinationIP)
    | where private == false
    // Filter out events where network connection was blocked - change this to expand hunt
    | where DeviceAction has_any ("allow", "accept", "allowed")
    | summarize by DestinationIP);
    CommonSecurityLog
    | where TimeGenerated between (ago(starttime) .. ago(endtime))
    | where ApplicationProtocol =~ "ldap"
    | extend private =  ipv4_is_private(DestinationIP)
    | where private == false
    | where DestinationIP !in (legacy_ldap)
    | where DeviceAction has_any ("allow", "accept", "allowed")
    | project-reorder TimeGenerated, SourceIP, DestinationIP, ApplicationProtocol, DestinationPort, SentBytes, ReceivedBytes, DeviceAction
    | extend timestamp = TimeGenerated
    | extend IP_0_Address = SourceIP
    | extend IP_1_Address = DestinationIP
```

## How to Investigate?

1. Validate the detection logic and why it is considered new
   - Confirm the event falls within the window from 24 hours ago up to 1 hour ago
   - Verify the destination is external (public DestinationIP) and the protocol is LDAP
   - Note that the destination IP is not present in the prior allowed-LDAP destination set from the same time window, making it a newly observed external LDAP destination

2. Profile the source and destination endpoints
   - Review the SourceIP to identify the internal host, subnet, or egress point involved
   - Enrich the DestinationIP with ownership/ASN and reputation context to understand who operates it
   - Determine whether the DestinationIP is a known vendor, hosted directory service, cloud provider, or an unexpected network

3. Assess the connection characteristics for intent
   - Review DestinationPort to confirm whether traffic is using standard LDAP (389) or other related ports
   - Examine SentBytes and ReceivedBytes to infer whether this looks like a brief probe, repeated authentication attempts, or sustained directory queries
   - Check whether there are multiple events to the same DestinationIP suggesting persistence or enumeration patterns

4. Correlate with identity and directory activity signals
   - Check for authentication activity from the same SourceIP around the same timestamps that could indicate credential use tied to LDAP
   - Look for directory query or enumeration indicators on the source host that align with outbound LDAP usage
   - Determine whether the timing coincides with user logons, scheduled tasks, or administrative sessions on the source system

5. Determine whether the source system should ever initiate external LDAP
   - Identify the role of the source host (workstation, server, identity infrastructure, security tooling, proxy) and whether outbound LDAP is expected
   - Review recent configuration or application changes on the source that could explain new external LDAP dependencies
   - Check whether similar outbound LDAP behavior exists from peer systems in the same role group

6. Scope the behavior across time and environment
   - Check whether the same SourceIP contacts additional external LDAP destinations or whether other internal hosts contact this same DestinationIP
   - Determine whether this is a one-off occurrence or recurring across multiple days (outside the 24h-to-1h window)
   - Document the observed pattern: which internal sources, which new external destinations, and the traffic volume profile
