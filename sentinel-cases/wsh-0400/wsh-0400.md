## WSH-0400 Rare RDP Connections

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why case _"WSH-0400 Rare RDP Connections"_ has been created, how to use it.

### Required MDR Modules and Sentinel Connectors

| MDR Module                       | Required Data Connectors            |
|--------------------------------- |------------------------------------ |
| **Identity Protect On-Premises** | Security Events via Legacy Agent or |
|                                  | Windows Security Events via AMA or  |
|                                  | Windows Forwarded Events (Preview)  |

### Custom Changes

* We only look for external IP's.

## Overview

This case was created to alert **on new RDP and rare RDP connections which haven't been seen during the previous 14 days** based on whenever this incident is triggered. It is important to keep in mind that not every new or rare RDP connection is malicious, as not every user has the need to frequently access their servers using the RDP protocol. However, once such connections are actually of malicious nature, you want to be informed about this - hence this usecase.

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **"Identity Protect module"**, specifically **"Identity Protect on-premises"** also known as **"Microsoft Defender for Identity"** within the Microsoft environment itself.

### How to detect?

For every in scope server (_see the table below_) the **"SecurityEvents"** need to be uploaded to the Wortell MDR Sentinel Log Analytics Workspace with the Microsoft Sentinel  **"Security Events"** connector (or the **"Windows Security Events via AMA"** connector or the **"Windows Forwarded Events"** connector depending on the situation).

| MMA/AMA Installation on:                     |
| -------------------------------------------- |
| Domain Controllers (AD DS)                   |
| Active Directory Federation Services (AD FS) |
| DNS (DNS)                                    |
| AAD Connect                                  |
| AD Certificate Services (AD CS)              |

Furthermore, monitoring for **"EventID 4624"** _(An account was successfully logged on)_ is needed. To receive “EventID 4624”, the following Audit Policy needs to be configured for “Success" and "Failure”:

* _Computer Configuration_ > _Policies_ > _Windows Settings_ > _Security Settings_ > _Advanced Audit Policy Configuration_ > _Audit Policies_

| Audit policy | Sub category | Triggers event ID |
| ---- | ---- | ---- |
| Logon/Logoff | Audit Logon | 4624 |

Additionally, the following policy must be configured:

* _Computer Configuration_ > _Policies_ > _Windows Settings_ > _Security Settings_ > _Local Policies_ > _Security Options_

| Policy | Value |
| ---- | ---- |
| Audit: Force audit policy subcategory settings (Windows Vista or later) to override audit policy category settings | Enabled |

For more information, see the [_"Windows Audit Settings Requirements"_](../../../Documentation/windows-audit-settings-requirements/windows-audit-settings-requirements.md)

### KQL

```kql
    let starttime = 14d;
    let endtime = 1h;
    (union isfuzzy=true
    (SecurityEvent
    | where TimeGenerated >= ago(endtime)
    | where EventID == 4624 and LogonType == 10
    | where ipv4_is_private(IpAddress) == false
    | summarize StartTime = min(TimeGenerated), EndTime = max(TimeGenerated), ConnectionCount = count()
    by Account = tolower(Account), Computer = toupper(Computer), IpAddress, AccountType, Activity, LogonTypeName, ProcessName
    // use left anti to exclude anything from the previous 60 days that is not rare
    ),
    (WindowsEvent
    | where TimeGenerated >= ago(endtime)
    | where EventID == 4624 and EventData has ("10")
    | summarize computerCount=count() by Computer < 10
    | extend LogonType = tostring(EventData.LogonType)
    | where  LogonType == 10
    | extend Account = strcat(tostring(EventData.TargetDomainName), tostring(EventData.TargetUserName))
    | extend ProcessName = tostring(EventData.ProcessName)
    | extend IpAddress = tostring(EventData.IpAddress)
    | where ipv4_is_private(IpAddress) == false
    | extend TargetUserSid = tostring(EventData.TargetUserSid)
    | extend AccountType=case(Account endswith "$" or TargetUserSid in ("S-1-5-18", "S-1-5-19", "S-1-5-20"), "Machine", isempty(TargetUserSid), "", "User")
    | extend Activity="4624 - An account was successfully logged on."
    | extend LogonTypeName="10 - RemoteInteractive"
    | summarize StartTime = min(TimeGenerated), EndTime = max(TimeGenerated), ConnectionCount = count()
    by Account = tolower(Account), Computer = toupper(Computer), IpAddress, AccountType, Activity, LogonTypeName, ProcessName
    ))
    | join kind=leftanti (
    (union isfuzzy=true
    (SecurityEvent
    | where TimeGenerated between (ago(starttime) .. ago(endtime))
    | where EventID == 4624
    | summarize by Computer = toupper(Computer), IpAddress, Account = tolower(Account)
    ),
    ( WindowsEvent
    | where TimeGenerated between (ago(starttime) .. ago(endtime))
    | where EventID == 4624
    | extend IpAddress = tostring(EventData.IpAddress)
    | extend Account = strcat(tostring(EventData.TargetDomainName), tostring(EventData.TargetUserName))
    | summarize by Computer = toupper(Computer), IpAddress, Account = tolower(Account)
    ))
    ) on Account, Computer
    | summarize StartTime = min(StartTime), EndTime = max(EndTime), ConnectionCount = sum(ConnectionCount)
    by Account, Computer, IpAddress, AccountType, Activity, LogonTypeName, ProcessName
    | extend timestamp = StartTime, AccountCustomEntity = Account, HostCustomEntity = Computer, IPCustomEntity = IpAddress
```

## How to investigate?

To investigate this usecase, investigate if RDP connections have appeared more often. Use the RDP query to see if the user used RDP before. Additionally use the On-Prem Account changes kql query to see if the user object had any changes.

### Standard Investigation Queries

The following queries have to be ran in order to investigate this incident:
