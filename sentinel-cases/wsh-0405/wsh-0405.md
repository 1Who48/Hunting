## WSH-0405 Crash dump disabled on host

## Document Classification

This document is only for internal use of Wortell Managed Detection and Response.

## Introduction

The purpose of this document is to explain why usecase _"WSH-0405 Crash dump disabled on host"_ has been created, how to use it.

### Required MDR Modules and Sentinel Connectors

| MDR Module                 | Required Data Connectors          |
| -------------------------- | ----------------------------------|
| **Device Protect**         | Windows Security Events via AMA   |

### Custom Changes

* No custom changes are made.

## Overview

This hunting case helps to detect the prevention of crash dumps being created. This can be used to limit reporting by malware, look for suspicious processes setting this registry key.

### MITRE ATT&CK

This attack tactic can be mapped on the MITRE ATT&CK framework:

| Tactic                | Techniques |
|-----------------------|------------|
| Defense evasion       | T1070      |

## Applicability & Technical Requirements

This use case is applicable to customers that subscribe to the Wortell MDR **Device Protect** module.

### How to Detect?

The **"DeviceActivity"** logs of the customer need to be exported to the Wortell MDR Sentinel Log Analytics Workspace with the Microsoft Sentinel **"Windows Security Events via AMA"** connector of Sentinel.

### KQL

```kql
    SecurityEvent
    | where TimeGenerated > ago(1d)
    | where EventID == 4657
    | parse ObjectName with "\\REGISTRY\\" KeyPrefix "\\" RegistryKey
    | project-reorder RegistryKey
    | where RegistryKey has "SYSTEM\\CurrentControlSet\\Control\\CrashControl"
    | where ObjectValueName =~ "CrashDumpEnabled"
    | extend  RegistryValueData = iff (OperationType == "%%1906", OldValue, NewValue)
    | where RegistryValueData == 0
    | extend NTDomain = tostring(split(Account,'\\',0)[0]), Name = tostring(split(Account,'\\',1)[0])
    | extend HostName = tostring(split(Computer, '.', 0)[0]), DnsDomain = tostring(strcat_array(array_slice(split(Computer, '.'), 1, -1), '.'))
    | extend Account_0_Name = Name
    | extend Account_0_NTDomain = NTDomain
    | extend Host_0_HostName = HostName
    | extend Host_0_DnsDomain = DnsDomain
```

## How to Investigate?

1. Validate the event context and change direction
   - Confirm the timestamp of the change and whether it occurred within an expected maintenance window
   - Review OperationType semantics for the record to understand whether the value was set to 0 or cleared during an update path
   - Note the exact registry path and value name to ensure the result is specifically CrashControl\CrashDumpEnabled

2. Identify the actor and logon context behind the change
   - Review the initiating account details (domain and username) and determine if it maps to an admin role, service account, or managed identity
   - Check whether the account’s activity around that time indicates interactive use versus automation (for example, scheduled task vs user session)
   - Confirm whether the account is local to the host or a domain account, and whether it is common for that host type

3. Correlate with adjacent Windows Security events to understand how the change was made
   - Look for nearby authentication and privilege-use activity for the same account and host (logons, elevated token use, special privileges assigned)
   - Check for evidence of remote administrative access around the event time (remote logon types, RDP, WinRM, SMB admin shares)
   - Determine whether the change aligns with a sequence that suggests manual registry editing, a script, or a management tool action

4. Determine the originating process and execution chain (if your telemetry supports it)
   - Pivot from the host and time window into endpoint telemetry to find the responsible process (common candidates include reg.exe, powershell, wmic, services.exe, gpupdate, management agents)
   - Capture parent-child process relationships to identify the launcher (interactive shell, scheduled task engine, management agent, remote execution service)
   - Review command-line patterns and script locations associated with the process to assess intent and scope

5. Assess whether this host behavior is isolated or part of a broader pattern
   - Check if multiple hosts show the same CrashDumpEnabled set to 0 within a similar time window, especially in the same OU, subnet, or role group
   - Compare affected hosts against known baselines (gold image, hardening standards) to see if this setting is normally enabled in your environment
   - Identify whether the same account is associated with similar registry modifications across other systems

6. Evaluate operational impact indicators without taking action
   - Confirm whether disabling crash dumps would materially reduce visibility for this host’s role (servers, critical workloads, security tooling hosts)
   - Review recent system instability signals (unexpected reboots, bugchecks, application crashes) to see if crash dump suppression could be relevant
   - Document the investigative narrative: who changed it, how it was changed, where it occurred, and whether it matches expected administrative behavior
